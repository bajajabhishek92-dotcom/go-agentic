Standing up a demo agent is easy. Production multi-agent systems fail for reasons prompts cannot fix: agents improvise paths, skip validation, and mishandle edge cases. You need cognitive architecture and execution flow—not only longer instructions.

Challenge map (Deep Insight pattern)

| Challenge | Design response | | --- | --- | | Control execution across agents | Graph of agents with conditional edges; specialized agents invoked as tools by a supervisor | | Right model per role | Cheap/fast model for routing; stronger model for planning; mid-tier for execution | | Operate reliably | Managed runtime with session isolation, private networking, monitoring | | Safe code execution | Ephemeral sandboxes per session for interpreter tools—no shared sticky containers | | Monitor and manage | Admin signals, failure alerts, identity for operators |

Plan then execute, with humans on the plan

Without an explicit plan, mid-course corrections invalidate work and users cannot see progress. A Planner decomposes into checklist steps assigned to specialists; a Plan Reviewer presents the plan for approval/revision (HITL) before a Supervisor runs it. Cap revision loops. Users can re-run a failed step instead of the whole job.

Compress handoffs

Each specialist works in its own context and returns compressed results. The supervisor orchestrates; coder/validator/reporter/tracker do not dump full transcripts into one window. Pair with prompt caching on stable role prompts.

Match model cost to cognitive load

A coordinator that only classifies greetings vs. analysis should not pay frontier rates. Planning with extended thinking may warrant a larger model. This is the same idea as platform-level model routing in FinOps playbooks.

Customer patterns that generalize

Across industries, successful deployments share structure:

  • Automated triage — Alert → agent gathers logs/health across tools → structured summary to chat in minutes (Circle K: mean triage under 15 minutes). Same shape for CI failure classification (Rescale) and IT help desks.
  • Exception workflows — Multi-agent handling of invoice/freight mismatches with clear categories and TMS integration (Worldwide Express: large cuts in active exceptions and time-to-cash).
  • Domain decision engines — Supervisor routes natural-language questions to specialists over existing ML/ops systems so users stop spelunking APIs and dashboards (Bayer Crop Science ADE).
  • Evidence assemblers — Multi-agent assistants that retrieve, score against deterministic rules, and draft packages while humans remain the decision-makers (engineering part substitution). Never auto-approve high-consequence substitutions.

Responsible controls when agents write code or reports

If agents generate executable code or external documents, isolate interpreters, validate calculations with a separate agent, cite sources, and keep HITL on plans or final high-stakes actions. Streaming UI progress reduces “black box” distrust during long runs.

Takeaway

Production multi-agent work is graph design, role-appropriate models, sandboxed tools, and operational isolation—plus domain patterns (triage, exceptions, decision support) that keep humans on irreversible decisions.

Frontier models are no longer judged only by short chat answers. The newest Gemini 4 class (Argon, then Carbon) is framed around deep work: multi-day engineering, multi-step professional workflows, and agentic runs that survive dead ends.

What “long horizon” actually means

A long-horizon task is one where a single brilliant response is not enough. The agent must:

  • hold a goal across many tool calls and hours (or days);
  • recover when a path fails;
  • keep producing useful artifacts (patches, refactors, analyses) without drifting off scope.

DeepMind’s Carbon announcement stresses sustained agentic workflows: root-causing subtle bugs across large codebases and low-level systems, not just completing a coding quiz. Argon’s public case studies make the same point with concrete engineering work—Chromium-scale refactors, overnight ADK performance work, and open-source package speedups—where the model ships multi-file change sets under a skills/rulebook harness.

Capability is rising with the harness

Long-horizon success is not only a model property. In Antigravity and similar platforms, the model is paired with:

  • skills / rulebooks that encode project conventions and goals;
  • multi-agent loops (e.g. visual critique, synthesis of many documents);
  • tools that ground work in real code, chemistry toolkits, or robotics APIs.

The teachable pattern: when horizon lengthens, invest as much in the environment and feedback loop as in raw model size. Overnight autonomous optimization only works if tests, metrics, and constraints are machine-checkable.

Alignment shows up as workmanship, not only refusal

Carbon’s safety narrative highlights behaviors that matter on long jobs:

  • fewer shortcuts and cheating attempts on terminal/coding benches;
  • fewer unsupported claims and clearer caveats when evidence is missing;
  • asking the user when sources disagree instead of guessing;
  • less overreach and less under-service on multi-step plans.

For builders, that is a product requirement: a long-running agent that fabricates completion or silently bypasses constraints is worse than a weaker model that reports blockers honestly.

Practical takeaways

  1. Design tasks with verifiable checkpoints (tests, diffs, Elo-style rankings of hypotheses)—not open-ended “finish the project.”
  2. Prefer staged autonomy: short trusted loops first, then longer overnight runs.
  3. Measure scope fidelity (did it stay in bounds?) alongside task success.
  4. Treat long-horizon models as pair engineers that need a rulebook, tools, and human review gates—not as fire-and-forget oracles.

Agent workflows are full of tiny judgments: classify this input, route that ticket, pick a next action, score severity. Calling a full generative responses endpoint for each one burns latency and money. When the answer space is bounded, specialize the API—and the model—around decision outputs.

Three answer shapes cover most micro-decisions

A Decisions-style interface asks a question with allowed answers and returns one of:

| Type | Meaning | Typical use | | --- | --- | --- | | Predicate | Probability a condition is true | “Is there visible damage?” | | Choice | One of predefined options (+ probs/confidence) | continue / retry / ask user | | Score | Weighted level on an ordered rubric | severity 0–n |

Context can be text, images, or native JSON. Batching many questions per request (hundreds) amortizes overhead for fan-out classification.

Why a dedicated path is faster

Focusing a smaller, efficient model (e.g. Luna-class) on bounded answers can be an order of magnitude faster than the same model through a general Responses API—because generation length, decoding, and product path are optimized for closed-form results. Pricing can charge for input only (no output tokens), with aggressive prompt caching for reused instructions and schemas.

Where it fits in the stack

  • Inside voice agents: on each transcript update, decide expression, escalation, or clarifying question without stalling the live conversation.
  • Inside product loops: categorize transactions, theme news coverage, attribute costs, gate interactive UI.
  • Beside heavy agents: let Astra/Sol-class models plan and use tools; let Decisions handle high-QPS gating and routing.

Design practice

  1. Start with one recurring decision your system already makes implicitly.
  2. Write the question, the exact option set, and the context features that distinguish options.
  3. Evaluate on real traffic slices for calibration (especially predicates and scores).
  4. Cache stable instructions/schemas; put volatile evidence last so cache hits stay high.
  5. Keep generative endpoints for open-ended work; do not force essays through a decision API or force classifiers through a chat API.

Teaching takeaway: agent cost curves are often dominated by many small open-ended calls. Closing the answer set is an architectural lever, not just a prompt trick.

Generic “use a browser” demos understate the hard problem: agents must operate specialized business software under company rules—approvals, templates, jurisdiction clauses, CAD constraints, QA viewports—and verify that the finished process works, not just that individual clicks succeeded.

Partner-defined tasks beat synthetic toy UIs

A productive research pattern:

  1. Pick a software vendor whose product embeds real enterprise rules (e.g. contracting platforms).
  2. Have practitioners enumerate high-value tasks (NDA setup, procurement approvals, clause updates)—often 30–40 minutes of expert work each.
  3. Score each attempt against dozens of criteria, not a single pass/fail, so you see which requirements the agent drops mid-flow.
  4. Provide hosted practice environments; generate synthetic variants; train with RL.
  5. Measure both accuracy and time per attempt.

In Ironclad-style contracting evals, a frontier computer-use model improved average score substantially while cutting estimated time nearly in half versus the prior generation—still far from perfect, which is the point: oversight and the full platform remain necessary when one forgotten rule breaks the process.

Physical and multimodal engineering follows the same logic

Computer use extends past SaaS into CAD, PCB tools, and manufacturing prep. Early experiments show agents can draft enclosures, boards, firmware, and UI for a device—and still miss manufacturer tolerances and assembly realities. Progress metrics (e.g. BenchCAD-style reconstruct/assembly scores) and industry review loops (motorsports reverse-CAD, automotive aero/crash simulation) are how you learn which steps are assistive today versus unsafe to leave unsupervised.

Runtime computer use in product QA

Beyond training, computer use lets review agents run the app: spin a PR’s server, resize to a phone viewport, visually spot a missing button that code review would miss. When shipping velocity rises with coding agents, static review alone under-covers behavioral bugs; UI-capable agents become part of the quality loop.

How to collaborate usefully with model labs

Bring: a concrete failing task, success criteria, people who know the work, a secure test environment, and data that can be used for research. Vague “make our product agentic” requests do not create training signal.

Teams shipping most of their code with AI assistants are not magically “prompting better.” They are practicing a stack of ideas that reuse classic computing patterns—feedback loops, orchestration, isolation—under new names. Five terms form a useful ladder from a single model call to an automated software factory.

Prompt engineering

Prompt engineering is crafting instructions the model should follow: role, constraints, “answer only from this documentation,” few-shot examples, chain-of-thought scaffolds for smaller models. Frontier models often respond well to long, spoken dictation; smaller local models benefit more from explicit examples. Domain expertise still matters: communication quality often outweighs raw model ranking for a given task.

Context engineering

The model sees more than your prompt. The context window holds the system prompt, tools and MCP servers, skills, retrieved documents, codebase slices, and conversation history. Quality can degrade before you hit the advertised window limit. Techniques include compacting history into a fresh summary, and spinning up sub-agents that research a library or doc without bloating the main window—then returning a short result.

Harness engineering

Two products can wrap the same model and feel completely different. Alone, a model is a “brain in a jar”: it cannot open files, run code, or browse. The agentic harness is everything around the model that lets it act, verify, and continue: tools, memory, sandboxes, orchestration, and the runtime that executes commands and feeds results back.

An agent is model plus harness. Inside the harness:

  • Tools — files, sandboxed code execution, web, computer use, shell, and MCP for external services.
  • Memory — instruction files like agents.md loaded each session; compaction when the window fills; search (grep or semantic) instead of dumping the whole repo.
  • Agentic loop — plan → act (via harness) → observe → repeat, often with continuous verification (tests, screenshots, a reviewer model).

Recent capability gains often come as much from better harnesses as from smarter weights. Asking “is AI good at X?” should become “which model and which harness?”

Loop and graph engineering

An agent is a loop: goal → act with tools → observe → decide success or continue. Loop engineering attaches triggers (cron, pull request opened, alert) so a system orchestrates agents toward a goal with humans approving critical steps—rather than a person hand-prompting every turn.

Graph engineering fans that loop into parallel agents (research vs. repo mapping vs. implementation) that hand off work. Useful for complex jobs; expensive if every branch burns tokens without discipline.

Software factory

A software factory automates the development lifecycle with task-specialized agents for implementation, testing, review, and operations—not one general agent doing everything. Each agent needs isolation (containers/sandboxes), identity (what it may access in Git or cloud), and observability (traces of overnight runs). Solo developers may never need a factory; prompt, context, and harness skills still apply to everyone.

From software engineering to agentic engineering

Traditional software engineering is largely deterministic: explicit control flow, same input, same output. Agentic engineering shifts effort toward shaping probabilistic behavior—goals, environments, constraints, verification—while humans remain accountable. On a spectrum: traditional coding → AI-assisted snippets → vibe coding (intent in natural language) → agentic coding (plan, tool use, iterate) → agentic engineering (designing the environment where autonomous systems operate under constraints).

Vibe coding prototypes fast; without structure it accrues debt. Agentic engineering insists the engineering did not disappear—it moved to orchestration and verification.

articlecorpus/ibm-ai-knowledgecluster/agentic-systems

Keywords: loop-engineering, agentic-engineering, ibm, agentic-systems, cluster-agentic-systems, corpus-ibm-ai-knowledge, article, loop, engineering, agent

Related: Agentic Engineering, Loop Engineering

Prompt engineering is writing the next perfect instruction by hand. Loop engineering is designing a system that takes a goal, prompts an agent, checks the work, prompts again, and repeats until a stopping condition is met—with minimal manual prompting, but not zero human responsibility.

The core loop

A simple agent loop has four stages:

  1. Goal — what “done” means.
  2. Act — for a coding agent: open files, edit code, run commands.
  3. Observe — read test output, errors, diffs.
  4. Adjust — try another fix or move on when a check passes.

The goal is evaluated every lap. Vague goals (“make checkout faster,” “be happier”) have no measurable end: the agent may loop forever or declare victory after one pass. A good goal is specific and verifiable—“stop when every unit test in the checkout suite passes.”

That skeleton alone does not deserve a discipline name. Loop engineering is everything built around the loop.

Triggers, context, spine, tools, sub-agents

Something must start the loop: a schedule (nightly cron) or a hook (file change, pull request opened). Hooks often enforce security and quality policies at events.

Every trip generates context—test output, file contents—that piles up and steals attention. Context engineering decides what the loop may see: compaction, progressive disclosure of skills (procedures for recurring jobs), and pruning of noise.

A spine is persistent state outside the ephemeral window: markdown notes of what was tried and what worked, informing later iterations.

Tools (MCP or direct APIs) let the agent execute: filesystem, terminal, databases. For observation, strong practice uses a sub-agent—a checker with its own instructions, context, and sometimes a different model—rather than asking the same writer to grade its own homework.

“Minimal” human involvement is a specific amount

Compared with hand-prompting, loops reduce human typing. They do not remove human duty. Four pitfalls show why:

  • Unverified code — a checker agent is still an agent. Humans remain responsible for shipped code; someone must read it.
  • Comprehension debt — the gap between how much code exists and how much humans understand. Agents write fast; unread code widens the gap and hurts incident response and migrations.
  • Intent debt — agents can see what a system does more easily than why. Without intent written where agents look (for example agents.md), a “fix” may relax discount validation to make tests green while hurting the business.
  • Cognitive surrender — blindly accepting loop output because “the AI did it,” which accelerates comprehension debt.

Humans should write the goal and stopping condition, keep intent visible to the agent, and read the output. Loop engineering works best when a human remains in that loop—not as rubber-stamp theater, but as the owner of goals, intent, and verification.

Specs and stopping conditions

Teams moving from chatty prompting to agent loops often adopt spec-driven goals: requirements and acceptance checks the agent can evaluate (tests green, lint clean, schema valid). That is loop engineering’s cousin to classical CI. Without a machine-checkable stop, “minimal human intervention” becomes either infinite spend or premature victory declarations.

Once models can run tool-calling loops reliably, the scarce skill is not “prompting an agent”—it is building the harness: the runtime that feeds context, tools, memory, sandboxes, and recovery around a deceptively simple loop.

The core loop is universal; the harness is the product

Harrison Chase’s definition is blunt: most agents are an LLM in a loop calling tools. A request arrives, the model generates, tools run, observations return, repeat. Every serious coding agent and enterprise agent is a variation of that loop.

What differentiates systems is what the harness inserts:

  • Middleware before/after model calls (summarization, context offloading, policy checks)
  • Tool wrappers (sandboxing, file systems, MCP/CLI/computer-use adapters)
  • Hooks and plugins (skills, subagents, memory)
  • Explicit cognitive architectures when the open loop is still too unreliable for a workflow

LangChain’s minimal harness and “Deep Agents” show the spectrum: start general, then specialize with middleware rather than rewriting a bespoke graph for every feature.

When to build your own

Build or deeply customize a harness when:

  • Domain tools emit huge, structured context that generic summarization mishandles
  • You need durable memory, workspace state, or multi-agent fan-out
  • Compliance requires deterministic checkpoints around tool use
  • Long-horizon work needs recovery policies the base loop does not provide

Stay on a general harness when you are still discovering the workflow. Premature cognitive architectures (2023-style rigid graphs) often fight the model’s improving ability to plan inside the loop.

Models that “eat the harness”

A recurring Sequoia theme: as base models improve, more of what lived in application scaffolding migrates into the model. Logan Kilpatrick’s “model eats the harness” tension is real—but so is the opposite pressure from enterprise tools, permissions, and proprietary systems. Expect a moving boundary: keep harness logic thin, measurable, and easy to delete when the model absorbs it.

Practice checklist

  • Implement agents as loop + middleware, not as one-off prompt trees
  • Put evals on harness behaviors (recovery, tool failure, context overflow), not only final answers
  • Prefer hooks you can turn off when a new model ships
  • Treat file system, skills, and subagents as product surface area, not infra trivia

Coding is the canary domain for agents: rich training data, fast verifiers (compilers, tests, types, CI), and developers willing to change tools. Sequoia conversations with Andrej Karpathy, Anthropic’s Boris Cherny, OpenAI’s Greg Brockman, and Factory’s Matan Grinberg describe the same arc from different angles—from autocomplete novelty to agentic engineering, the discipline of coordinating fallible agents so they ship faster without dropping the professional quality bar.

Definition: vibe coding vs. agentic engineering

Karpathy coined vibe coding for the moment when you stop micromanaging completions and start trusting a coherent agentic workflow to fill in large stretches of a codebase. In his framing, vibe coding raises the floor: more people can build software, and side projects multiply because the cost of attempting something collapses.

Agentic engineering is the complementary discipline. It is not “let the model cook.” It is preserving—and then extrapolating—the quality bar of professional software while agents do more of the typing. You are still responsible for vulnerabilities, design coherence, and whether the system does what the business meant. Agents are “spiky”: powerful, stochastic, sometimes brilliant, sometimes wrong. The engineering problem is how you coordinate them.

That distinction matters commercially. Teams that only raise the floor ship prototypes. Teams that practice agentic engineering ship systems they can operate, audit, and evolve.

Mechanism: what actually changed

Three technical shifts made the transition feel discontinuous rather than incremental.

Longer coherent horizons. Earlier tools were good at chunks—functions, refactors, local edits—and still needed constant human glue. Karpathy dates a sharper change to late-year agentic workflows that could stay on a task long enough to feel like a coworker, not a completion engine.

Harnesses as the product surface. Cherny’s Claude Code story is extreme but instructive: pick languages and frameworks that are “on distribution” for the model, then let the model write essentially all of the code. His personal setup pushes further—multiple sessions, nested sub-agents, and scheduled loops (cron-like jobs) that babysit PRs, heal flaky CI, and cluster feedback. The mechanism is not a single prompt; it is a runtime that schedules work, recovers, and keeps the factory moving while humans sleep.

Verification moves into the loop. Agents that can run shells, tests, and browsers close the feedback cycle that used to require a human after every guess. Factory’s Matan Grinberg emphasizes harness details that look boring until you operate at scale: caching economics, behavior under context compaction, and how tools validate work in the environment. A model-agnostic harness, in his view, avoids overfitting to one lab’s quirks—useful when the frontier model of the month keeps changing.

Cherny’s claim that “coding is solved” is best read as a local claim: for codebases and languages on-distribution for current models, the marginal cost of generating working code collapsed. He is explicit that huge, weird, off-distribution systems are still hard—and that waiting for the next model is often the real roadmap. Product value therefore migrates to orchestration, verification, problem selection, and review.

Practice: what builders actually own

If agents write the diffs, humans own a different stack:

  • Intent and constraints. Specs, acceptance criteria, non-goals, security boundaries, and “what must never regress.”
  • Architecture and taste. Karpathy’s examples are vivid: agents invent awkward account/email dualities; humans still decide identity models, aesthetics, and which tradeoffs are allowed.
  • Eval loops. Tests, types, canaries, replayable trajectories, and metrics for escaped defects—not vibes about “the PR looks good.”
  • Attention allocation. Brockman generalizes beyond code: once doing is cheap, human attention—is this good, wanted, aligned with values and policy?—becomes scarce. Products should conserve and route attention (escalation vs. auto-approve), not only burn tokens.

Grinberg’s “dark factory” prediction sharpens the ops picture: a large share of coding tokens may eventually run asynchronously—software building itself off the critical path of a human sitting in an IDE—while CIOs start justifying tokens the way they justify headcount. That only works if asynchronous work is instrumented: ownership, provenance, rollback, and cost controls. Enterprise adoption often passes through messy phases (encourage usage → measure usage in perf → cost rationalization). Designing for phase three early beats discovering token bills after culture mandates “use AI for everything.”

Failure modes

  • Vibe coding in production. Raising the floor without a quality bar introduces vulnerabilities and unmaintainable glue.
  • Puzzle hiring for an agentic job. Karpathy notes that LeetCode-shaped screens miss the skill that matters: take a large project and drive agents to a finished, good system.
  • Harness theater. Claiming a magical harness without metrics on compaction, tool validation, recovery, and cross-model robustness.
  • Attention bankruptcy. Generating more PRs than anyone can responsibly review; missing governance for derived artifacts when permissions change upstream (Brockman’s knowledge-base example).
  • Synchronous-only workflows. Forcing every agent turn through a human in the loop when the work is babysitting CI—or the opposite error: fully async with no owner when judgment is required.
  • Model lock-in without an exit. Betting the business on one lab’s UX while the frontier rotates; Grinberg argues modular, model-agnostic systems are the enterprise hedge.

Practice checklist

  • Treat tests, types, and CI as agent fuel—invest before you scale agent concurrency
  • Write executable specs (acceptance tests, invariants) agents can chase without guessing intent
  • Make review first-class: diffs with citations, replay, and clear escalate-vs-auto-approve paths
  • Track escaped defects from agent-authored changes as a core quality metric, not a footnote
  • Prefer harness behaviors you can measure (recovery, compaction, tool success) over lore
  • Hire and promote for large-project agent orchestration, not only solo puzzle speed
  • Budget human attention: design products that allocate scarce review, not only generate output
  • Plan for asynchronous “dark factory” work with ownership, cost controls, and rollback

Sequoia’s AI Ascent framing is intentionally non-academic: stop arguing about AGI checklists and notice that the shape of software work has changed. Pat Grady’s keynote metaphor is the teaching device—faster horses vs. cars—paired with Konstantine Buhler and Jim Gao’s economic story of a cognitive revolution, and Sonya Huang’s push for companies to own their intelligence rather than rent a black box forever.

Definition: a commercial AGI test

Grady refuses a laboratory definition of AGI. Sequoia studies founders, markets, and businesses. The commercial / functional test is practical: if you can dispatch an agent to do a job, and it can recover from failure and persist until the job is done, you are—functionally—in an AGI-like regime for work, even without technical consensus on “AGI.”

That definition is useful because it is falsifiable in a product sense. Demo chat that answers questions is not the test. Long-horizon agency that finishes jobs is.

Mechanism: communication revolutions vs. computation revolutions

Most founders alive today lived through communication revolutions—internet, cloud, mobile—where the breakthrough was distributing information. AI, in this framing (Grady credits partner Konstantine), is a computation revolution: how information is processed. That sounds semantic until you feel the product consequence: the foundation under your application moves continuously. New capabilities arrive as discontinuous jumps, not only as nicer UX on a stable substrate.

Grady highlights three inflection points:

  • ChatGPT / pretraining — the world saw what large-scale pretraining unlocked.
  • Reasoning models — a second scaling law around inference-time compute.
  • Long-horizon coding agents — agents that can work across extended tasks (he points to the Claude Code moment as the public reveal).

These look like points on a continuum; commercially they feel like a discontinuous change in what software is.

Faster horses vs. cars

Earlier AI applications made people roughly 10–40% more productive without changing the job—faster horses. The new generation aims for roughly 10–40× and reorganizes the work itself—cars. You do not ride a car the way you ride a horse, and you do not build a car company like a stable.

Organizational implication: if agents change the nature of work, they also change the nature of the company—team shapes, review rituals, what “headcount” means, and which roles are leverage vs. bottleneck. Pretending cars are horses leads to bolting a chatbot onto a process designed for manual throughput.

The $10 trillion cognitive-revolution frame

Buhler/Gao’s economic story pairs with the metaphor: the cognitive revolution is likened to the Industrial Revolution—as big or bigger, and faster—with a $10 trillion (10^13) opportunity framing. Cognitive work sits where physical labor sat during industrialization: an enormous pool of economic activity about to be re-factored.

Two vectors matter for builders:

  • Tech-out (labs): pushing general capability, models, and platforms outward.
  • Customer-back (application companies): specializing general intelligence into workflows that produce revenue, retention, and proprietary learning loops.

The specialization imperative—general components plus specialized labor/systems to produce specific outputs—explains why application companies still matter after foundation models exist. Steam engines did not end industry; they forced specialization. Likewise, startups (and startups not yet formed) specialize intelligence into vertical work.

Huang’s “own your intelligence” remarks sharpen the strategic fork: centralized intelligence that sucks in the world’s data exhaust vs. more decentralized ownership where firms keep workflow knowledge, weights, and evals as compounding assets. Cars-not-horses builders tend to choose customer-back moats—workflows, data rights, distribution—over wrapping the latest demo.

Affordance and diffusion gaps

A recurring Ascent theme: model capabilities are created faster than Fortune 500 deployment can absorb them. Every day the foundation models move faster than enterprise diffusion, the gap is opportunity—for products that create paths of least resistance (affordance) and for founders who build from the customer back.

Failure mode: shipping “AI features” that assume users will reorganize themselves around a model release. Cars need roads, fueling, and new driving norms—not a saddle with a motor.

Failure modes

  • AGI-debate distraction. Waiting for a technical definition while customers already buy job-finishing agents.
  • Horse-speed product roadmaps. Optimizing for 20% productivity skins instead of workflow reinvention.
  • Lab-demo moats. Wrapping a frontier model with thin UI while competitors own the workflow and data.
  • Static architecture. Systems that cannot absorb a new model release become liabilities when the floor keeps moving.
  • Ignoring diffusion. Building only for AI-native teams and leaving enterprise affordance (permissions, audit, change management) unsolved.

Practice checklist

  • Use the commercial test: can an agent recover and finish the job—not merely chat about it?
  • Design for 10–40× workflow change, not only 10–40% assistive speedups
  • Build moats customer-back (workflows, proprietary data, distribution), not demo-forward
  • Assume the capability floor keeps moving; keep architecture model-swappable
  • Close affordance gaps: permissions, audit trails, escalation, and deployment paths enterprises will actually use
  • Track diffusion lag as a product opportunity, not only as “enterprises are slow”
  • Decide explicitly what intelligence you own (evals, weights, environments) vs. rent

Classic RAG embeds a question, fetches nearest chunks from one index, and generates once. That design is right for many FAQs. It fails in recognizable ways on enterprise questions: answers that span two corpora come back fluent but incomplete; the right source depends on the question but a single index cannot choose; a second look after seeing first results has nowhere to happen.

What agentic retrieval adds

Put a reasoning agent in the retrieval loop. The agent decides:

  • Whether to retrieve at all.
  • Which knowledge base (or corpus) to consult.
  • Whether to retrieve again before composing an answer.

The output should stay grounded and cited—passages the reader can audit—not free recall dressed as facts. Managed knowledge-base products increasingly expose this as a first-class API (multi-turn planning, tool-driven retrieval, streaming cited answers) rather than a custom orchestration you maintain forever.

Ingestion quality still dominates answer quality

Agentic loops cannot fix garbage chunks. For web content:

  • Prefer a managed crawler for authorized public sites (robots.txt, rate limits, scheduled sync, JS wait) when it can reach what you need.
  • Add a preparation step when you need main-content-only Markdown, boilerplate pruning, CSS-bounded extraction, or custom metadata attributes for filtered retrieval. Write Markdown plus a metadata sidecar to object storage, then ingest through an S3-backed data source.

Preparation is batch ingestion of known properties—not real-time web search at inference time. Different problem.

Corporate document assistants (multi-language SharePoint, policies across countries) often win by using a fully managed knowledge base so product teams do not operate vector clusters, embedding pipelines, and sync jobs themselves—while still tuning chunking, metadata filters, and citation behavior.

Observability is mandatory once retrieval loops

A single-shot pipeline is a function you can read. An agent that retrieves in a loop takes a different path per question. By default you see neither the path nor whether the answer was good. Instrument:

  • Which tools/KBs were called and in what order.
  • Latency, tokens, and retrieval hit quality.
  • Faithfulness / grounding scores (on-demand and continuous).
  • Citations back to source passages.

Provision dashboards and evaluation with the same infrastructure-as-code that deploys the agent—do not bolt them on after the first production incident.

Access control for RAG is its own topic

Semantic search without permission checks is a data leak. Prefer verifying ACLs with the authoritative source at query time, not only filtering on ACL snapshots copied at last sync. See the companion article on multi-tenant and RAG access control.

Takeaway

Use single-shot RAG when one corpus and one fetch suffice. Graduate to agentic retrieval when questions need routing, multi-corpus joins, or iterative look-ups—and invest equally in clean ingestion, citations, and path-level observability.

When teams start building agents, the capabilities they need usually already exist as internal REST APIs. The hard part is not writing new product logic—it is making hundreds of private endpoints safely reachable by agents without public exposure, without letting the model invent identity, and without stuffing a 400-tool catalog into every prompt.

Anti-pattern: one MCP server per team

Giving each product team its own MCP server looks clean on a whiteboard and fails in operations:

  • Dozens of servers to patch and keep protocol-compatible.
  • Cross-domain agents must connect to many servers and reconcile them.
  • Every team needs MCP expertise unrelated to their product work.

A better org rule: product teams build REST APIs and declare which operations are tools; a platform team owns the MCP/protocol layer end to end. A team’s responsibility ends at a well-described OpenAPI (or similar) spec.

Four constraints that must hold together

Any workable architecture has to satisfy all of these at once:

  1. No public endpoints for internal APIs—private connectivity that does not require a new network change per API.
  2. Identity is not a model parameter — tenant, user, role, and DB context must be injected by the calling service (headers, tokens), never as LLM-visible tool arguments the model can invent or override.
  3. Authorization before catalog serialization — agents that should not call writes must not receive write tools in tools/list. Client-side filtering after the full catalog crossed the wire is not an authorization boundary.
  4. Discovery that scales — at ~50 tokens of schema per tool, hundreds of tools blow the context budget before reasoning starts. Prefer server-side policy scoping plus semantic search (“find tools for this intent”) so only candidates enter context.

Pattern: OpenAPI in, tools out

A managed gateway that registers OpenAPI specs as targets and generates tools from operations removes undifferentiated work:

  • Spec change → tool change; add/remove endpoints without writing MCP server code.
  • Policy engines (for example Cedar-style permit/forbid by principal and tool group) evaluate before the catalog is built.
  • Managed private egress reaches VPC-local services without per-integration NAT/VPN sprawl.
  • Semantic search over tool descriptions reduces rename fragility: agents find “segment user count” even if the operationId changed.

Write tool descriptions for models, not developers

API docs say what an endpoint returns. Tool descriptions must say when to call it and what to pass. Reusing developer docs verbatim trains the model to pick tools by implementation detail (“paginated list”) instead of intent (“find campaigns by status or channel”). Keep an explicit opt-in flag so cache-warmup routes never become tools by accident.

Search-first agents

New agents can start with zero hardcoded tool names: one meta-tool to search, then call what comes back. When teams rename or ship endpoints, agents pick them up without a code change—as long as descriptions stay accurate.

Takeaway

Separate concerns the way engineering orgs already work: APIs and OpenAPI belong to product teams; protocol, policy, and private connectivity belong to the platform. Treat identity as infrastructure headers, authorize before listing tools, and discover by intent so context windows stay for the task.

Agents that answer business questions from live systems need more than a chat model and a SQL dialect. They need joins, metric definitions, and row/column security to live outside the prompt—in a governed semantic layer the model plans against but does not invent.

Three layers an agent needs

  1. Planning model — chooses tools and writes queries (or structured tool calls).
  2. Semantic / knowledge layer — business meaning, join graphs, metrics, and access rules.
  3. Operational systems — warehouses, OLTP, SaaS, even on-prem databases, often federated.

When meaning lives only in the prompt, every agent reimplements “what is active customer?” and every change is a prompt deploy. When meaning lives in a semantic layer, BI tools and agents share the same definitions.

Authoring surfaces that travel beyond AWS product names

Production patterns seen across implementations:

  • Comments and aliases next to operational data — business meaning in database comments; foreign keys crawl into join paths; grants and row-level security apply per caller while the prompt and agent code stay the same.
  • Data virtualization — derived views over Aurora, Redshift, on-prem Postgres, and beyond; agent speaks a SQL dialect against governed views, not raw tables.
  • Dimensional models — attributes, hierarchies, facts, metrics in a modeling language (often Git-versioned YAML), exposed simultaneously over SQL, BI protocols, and MCP for agents.
  • Knowledge graphs — ontology-based concepts and relationships with a graph query language as the federation unit.

The common architecture: foundation model plans; MCP (or similar) exposes the semantic tool catalog; an agent runtime hosts the agent and manages outbound credentials to the semantic layer; filters for the caller stay in the layer, not in free-text instructions.

Governance that changes answers without changing prompts

The same agent code and tool catalog should return different rows for different roles because Postgres GRANT / RLS, virtualization policies, or dimensional security already constrain the caller. That is the point: identity of the human (or OBO token) flows to the layer; the model never receives another tenant’s schema.

Capture query traces (OpenTelemetry → queryable rows) so you can audit which SQL/VQL ran for which question—required when agents touch regulated customer-360 data.

When to use this vs document RAG

  • RAG / knowledge bases — unstructured policies, PDFs, tickets, manuals.
  • Semantic layers — live metrics, entities, and joins that must stay consistent with operational truth.

Many enterprise assistants need both: documents for “why,” semantic queries for “what is the number right now.”

Takeaway

Do not teach every agent your warehouse schema. Put business meaning, joins, and security in a semantic layer; expose it as tools; keep the model as a planner that never owns the definitions.

Classic RAG cuts documents into chunks, embeds them, and at query time retrieves the most similar fragments for the model. It is cheap and effective for many “find anything about X” questions over large corpora. It breaks down when the answer depends on document structure—or when structured facts and unstructured policy live in different systems.

What chunking throws away

Authors write trees: titles, sections, subsections, tables, figures, reading order. Chunking flattens that tree. Headings detach from the paragraphs they introduce; tables split from the sentences that explain them; cross-section answers become guesswork from unrelated blobs. Similarity search never knew those sections belonged together.

Chunkless RAG (as framed around Docling-style pipelines) keeps the tree. An agent starts from an outline with short section summaries, reasons about which branch likely holds the answer, opens that section, follows references, and walks a few steps—the way a person uses a table of contents. Benefits:

  • Path context — while reading a paragraph, the agent still knows its section path; a similarity chunk often does not.
  • Cross-document-section questions — hold place, read another branch, return.
  • Cleaner grounding — the model reasons over the right shaped material instead of inventing bridges between fragments.

The hard part is obtaining the tree. PDFs are paint instructions for glyphs, not clean structure. Tools such as Docling reconstruct a document object: real sections, reading order, intact tables. Agents can then navigate, extract, and enrich that object. Cost: more model round-trips and latency than one vector lookup; parsing quality is most of the engineering. Vector RAG still wins for fuzzy search over millions of docs. Many systems combine both: similarity to find the document, structure to navigate inside it.

When the corpus itself is messy

Even perfect retrieval fails if the document set is contradictory. Policies from different decades, federal vs state rules, legal opinions vs statutes, or colloquial “2019 vs 2020 championship” naming can all yield multiple “correct” answers. Practical mitigations:

  • Document hygiene — do not index superseded policies alongside current ones (unforced errors).
  • Clarification loops — make underspecified questions specific before answering.
  • Honesty about multiplicity — if a human reading the corpus would say “X, Y, or Z depending on context,” the system should too. Presenting opinions as facts looks like hallucination when it is really bad product design. The AI must be ≤ the data: it cannot be more certain than the sources allow.

The digital librarian pattern

Many business questions split into what vs why. The what (was the claim denied? what was the balance?) lives in SQL. The why (which policy paragraph?) lives in PDFs behind a vector index. A digital librarian agent: understands the question; decides which parts need SQL vs semantic search; builds and runs both queries; compiles results; answers with grounded insight. LLMs handle interpretation and synthesis; tools execute deterministic queries and light formatting. The shift is from retrieving silos to delivering answers that stitch them.

Structure-aware retrieval, careful corpus governance, and agents that know when to query which store are how complex documents stop defeating RAG.

Agents are only useful when they can act: open tickets, read repos, post to chat, query databases. How that connection is wired determines whether you get a demo or a governable system. Five patterns appear in practice, each adding more identity and less credential sprawl than the last.

5 — Direct connection with shared credentials

The agent calls a tool with an API key or service identity. Simple, reuses existing integrations, and was common in early RAG and agent demos. The tool never sees the end user—only the agent’s credentials—so teams often restricted access to broadly public or company-wide data. Fine for low-sensitivity prototypes; weak for user-specific authorization.

4 — Direct connection with OAuth to the tool

The agent talks to tools (GitHub, Jira, Slack, and similar) that speak OAuth. The tool challenges for user auth, issues an access token, and the agent stores it (as many coding assistants do locally). Pros: established OAuth, real user authentication. Cons: the agent impersonates the user—the tool may not distinguish agent vs human—and tokens can be long-lived (weeks), increasing replay risk if stolen.

3 — Insert MCP as an abstraction layer

Model Context Protocol sits between agents and tools. Agents speak MCP; MCP servers know how to talk to each backend. OAuth to the application can remain, but every agent no longer needs bespoke knowledge of every tool’s API. The win is portability and thinner agent code—not automatic security maturity.

2 — On-behalf-of with token exchange

Drop naive OAuth-only flows in favor of delegation: authenticate the agent as well as the user; the user delegates work to the agent; token exchange propagates access securely. Systems see both identities—what the user may do and what the agent is allowed to do—improving observability and ending pure impersonation. Visibility of user and agent is the point.

1 — Vault-issued short-lived credentials

Long-lived user tokens stored beside the agent remain a liability. Pattern one stores durable secrets in a vault and issues short-lived credentials to MCP for each flow. Intercepted tokens expire quickly; blast radius shrinks. Combined with MCP and on-behalf-of semantics, this is the strongest of the common patterns: authenticated user, authenticated agent, abstracted tools, short-lived creds.

How to choose

Climb the ladder as sensitivity and blast radius grow. Public FAQ retrieval can live at pattern five. Customer data and write actions need user visibility, agent identity, and short-lived credentials. MCP alone does not equal security—but it is the right seam at which to enforce policy, vaulting, and exchange once agents proliferate across the enterprise.

Why identity crisis language keeps appearing

Security practitioners increasingly treat agents like privileged identities: they authenticate, hold broad tool access, and act faster than a human session. Cost-of-breach style findings that most AI-related incidents lacked proper access controls reflect the rush to connect tools before climbing this pattern ladder. Pair MCP adoption with vaulting and exchange; otherwise you only standardized the attack surface.

Context Engineering: Giving Agents the Right Information

articlecorpus/ibm-ai-knowledgecluster/knowledge-access

Keywords: context-engineering, agent-harness, ibm, knowledge-access, cluster-knowledge-access, corpus-ibm-ai-knowledge, article, context, agents, information

Related: Agent Harness, Context Engineering

Prompt engineering asks how to phrase instructions. Context engineering asks a broader question: what entire information environment should the model see at each step? For agents that plan, call tools, retrieve documents, and run for hours, that distinction is decisive.

Context is everything present at inference time: system prompt, user task, project instructions, tool definitions, retrieved documents, message history, tool results, and memory. Context windows have grown into the hundreds of thousands or millions of tokens—but bigger windows do not automatically mean better agents. Studies of frontier models show reliability can fall as context grows. Researchers call this context rot: more tokens competing for a finite attention budget.

Right context beats more context

Models do not retrieve from context the way a database looks up a row. Every token competes for attention; material in the middle of a long window is often used less reliably than material at the edges. Dumping an entire repository, weeks of logs, or dozens of unused tools into the window therefore hurts.

Good context has four qualities:

  • Relevance — each piece helps the current task.
  • Structure — labels and formatting help the model separate instruction from data from tool output.
  • Timing — introduce information when needed, not all at once.
  • Compression — summarize or filter instead of pasting raw dumps.

Context processing turns raw material into usable form. Context management decides what to keep, discard, prioritize, and refresh across turns so the window stays coherent as the world changes.

Four failure modes of long agent runs

When agents migrate codebases or chase long goals, the window fills with system prompts, agents.md-style project files, tool schemas, step history, and large tool results. Four failure modes appear repeatedly:

  1. Context poisoning — a false conclusion (for example, a misread note that “retries are automatic”) enters the window and is treated as ground truth. The agent then deletes good code based on its own mistake.
  2. Context distraction — long history becomes the strongest pattern. The model continues doing more of what it already did instead of asking what the goal needs next.
  3. Context confusion — too many tool definitions make selection harder. In one benchmark, a model failed with 46 tools and passed the same task with 19.
  4. Context clash — superseded and corrected facts both remain, so the window disagrees with itself.

The remedies deliberately throw information away: validate conclusions before writing them into context; compact long history into summaries (and prefer durable files over endless window growth); curate tools to the job; prune outdated claims or start a fresh window with the corrected state.

Context for coding agents

A one-line request—“add a login endpoint”—cannot encode years of repo decisions. The same ask should yield FastAPI-and-Pydantic code in one repository and a Go handler in another. Useful agent inputs include:

  • searchable existing code and a compact repo map (files and symbols);
  • dependency lock files so APIs match real versions (many “hallucinated” functions are version mismatches);
  • tests the agent can run as a feedback loop;
  • conventions and constraints in a checked-in instructions file such as agents.md;
  • developer intent—what done looks like and what not to touch—which the repo alone cannot reveal.

If you do not yet know what to ask, have the agent interview you, explore and explain the repo, and list its assumptions before coding—then write what it learned back into the instructions file. Start fresh sessions per task; point at specific files; clear noise when a session grows long.

The goal is not maximum context. It is the minimum information that keeps the agent accurate while leaving humans in charge of decisions.

An agent facing a production 500 error will flounder if you only dump runbooks, dashboards, and customer history into the context window. Four complementary mechanisms give agents knowledge beyond training data—each for a different kind of knowing.

A working rule of thumb

| Need | Mechanism | |------|-----------| | Written-down knowledge (docs, manuals) | RAG | | Lessons the agent learned from prior runs | Memory | | Repeatable procedure and judgment (“how we triage”) | Skill | | Live reach into systems without custom glue per tool | MCP |

Skills: procedural knowledge on demand

A skill is instructions—and sometimes code—for doing a particular job the model was never trained on: steps, when to escalate, stopping rules. Formats are often a folder with a skill.md (YAML name/description plus markdown body). Progressive disclosure matters: at startup the agent may see only names and descriptions; it loads the full body when the task matches.

Best practices from production skill building:

  1. Description is the trigger — say what the skill does and when to use it; models under-trigger, so slight overselling beats vagueness.
  2. Build from real expertise — walk the task yourself or mine runbooks/PR feedback; put gotchas in the body (environment facts that defy reasonable assumptions).
  3. Spend context wisely — keep bodies lean (~500 lines / ~5k tokens guidance); put deep material in references/ opened only when needed.
  4. Deterministic scripts for fragile steps — math, exact transforms: scripts/ the agent runs, not improvises.
  5. Vet before running — skills can execute code and touch files/keys; treat third-party skills like dependencies (audits have found high rates of flaws in public skill corpora).

A triage skill can say “check error rate, then recent deploys”—but cannot by itself read the dashboard.

MCP: reach into the world

Model Context Protocol sits between the agent (MCP host) and systems behind MCP servers. The model need not know a proprietary logging API; the server exposes callable capabilities. With MCP, “check error rate” becomes a real metrics/logs call. Skills tell what to do; MCP enables doing it through a shared protocol instead of one-off integrations per agent.

RAG vs memory

RAG retrieves from documents people deliberately indexed (often a vector store) via semantic search, injecting matching chunks when needed. Memory is what the agent itself stored from experience—last time this 500 was caused by X, not the runbook’s Y—and can write the fix back after resolution. Same “pull when needed” shape; different provenance.

Putting them together

For the checkout outage: skill structures triage; MCP fetches live signals; RAG supplies dependency maps and manuals; memory recalls last week’s ugly root cause. Stuffing everything into the window is not a substitute for choosing the right mechanism for each kind of knowledge.

Five-stage loop

Run these as a continuous cycle. Jumping to “optimize” without attribution is guessing.

1. Attribute every dollar

Invoice-grade attribution to an IAM (or equivalent) principal that made the call, tagged with team, application, and cost center. Billing pipelines lag (~24h). Invocation logs plus request metadata (application, workflow, tenant, agent) answer what generated tokens within minutes. Inject metadata centrally in an SDK wrapper or gateway—do not trust every app to invent a consistent schema. Dashboards should show leaders by caller and by workflow.

  • Alert only — budgets/notifications; no hard stop.
  • Async deny — counters from logs; attach deny policies or withhold credentials after breach (seconds–minutes lag).
  • Synchronous gateway — HTTP 429 at the limit; model allow-lists and routing; component must sit in the data path.

Phase up as spend and risk grow. Alerts first; hard blocks when velocity demands them.

4. Optimize platform defaults

Most waste is defaults nobody set:

  • Model routing — send boilerplate to smaller models; reserve frontier for hard reasoning. Validate with evals on the workload leaderboard.
  • Prompt caching — agents re-send tools, instructions, and history every turn (“Groundhog Day”). Cache stable prefixes; keep variable fields (timestamps, request IDs) after the cache breakpoint. Track cache-read vs cache-write ratios—writes never re-read are pure loss.
  • Token limits and tool-result compression — trim observations so multi-step loops stay inside context and budget.

5. Operate on a cadence

A small scorecard (cost per agent task, cache hit rate, % calls on cheaper models, budget breaches) reviewed jointly by FinOps and platform engineering turns data into routing and design changes.

Agent-specific caching patterns

On each turn the model must see tools, instructions, history, and the new message—it has no internal memory between HTTP calls. Explicit breakpoints mark reusable tool+instruction prefixes across sessions and sub-agents; implicit caching follows the growing conversation. Serialize tools identically every time or the prefix never matches.

Takeaway

Cheaper models help after you can attribute, observe, and enforce. Build the operating loop; treat agentic token multiplication and prompt caching as first-class platform concerns.

Structural compression (fewer layers/heads/params) plus aggressive quantization usually loses quality. The usual fix is quantize then heal. How you heal decides whether 4-bit stays a permanent tax—or becomes another teaching pass.

Why QAT and QAD struggle after compression

  • Quantization-aware training (QAT) — fake-quant in the forward pass + task loss. Expensive (re-runs SFT/RL-style post-training) and can collapse if training continues past the peak: one matched experiment peaked late then lost nearly 19 points by step 1,200.
  • Quantization-aware distillation (QAD) — KL from a frozen full-precision teacher into the quantized student. Works when teacher and student share architecture. After structural compression, the only “full-precision twin” is often a recovered bfloat16 checkpoint that is itself a degraded distillate—so the student inherits that ceiling.

QAH’s move: distill from the original teacher

Quantization-Aware Healing (QAH) distills the quantized, structurally smaller student from the original pre-compression model, not from the recovered mid-checkpoint. Architectures need not match: the teacher’s output distribution is architecture-agnostic; the student only matches logits via KL. Quantization becomes a second distillation pass against the true teacher—supervision the recovered BF16 never fully absorbed—rather than mere damage control.

Long-context healing (documents up to 32k) needs memory-efficient chunked KL so the full vocab×sequence grid never materializes (companion efficient-distillation work).

Headline pattern on GPT-OSS 120B → 60B MXFP4

Against the recovered 60B BF16, the QAH 4-bit student won 7 of 9 reported benchmarks, with large gains on long-context reasoning and math—exactly where compression often hurts most. Peak accuracy vs QAT was similar, but QAH peaked ~7× sooner (~100 vs ~700 steps) and stayed stable; QAT drifted after peaking.

Local quants without leaving transformers

Separately, transformers can load GGUF packs (llama.cpp-style quants) via from_pretrained(..., gguf_file=...) with Hub kernels keeping weights packed on Metal when available. Start with practical mid quants (for example Q4_K_M), then step up (Q5_K_M, Q6_K) if quality on your evals demands it. Without a compatible kernel, loaders may dequantize and erase the memory win.

Practice checklist

  • After prune+quantize, prefer healing that can still learn from the pre-compression teacher.
  • Prefer KL-to-frozen-teacher for stability over unbounded CE task loss when shipping 4-bit.
  • Keep an early-stopping signal for QAT; assume QAH still needs validation but drifts less once matched.
  • For local serving, evaluate GGUF variants on task suites—not only on “fits in RAM.”

Two kinds of tokenizer waste

  1. Fragmentation — domain-repeated spans (JSON envelopes, competency names, boilerplate) split into many tokens every request.
  2. Excess — tens of thousands of vocabulary entries the domain never emits, yet the LM head scores every entry on every decode step.

On a 4B-class model, the LM head can be ~10% of parameters. Prefill reuses weight reads across input tokens (compute-bound); decode is often memory-bound. In their measurement, a generated token cost ~7.4× a read token. Compressing input and output equally therefore misses most of the savings—outgoing tokens are the expensive boxes.

Cost, not frequency

Classic vocabulary adaptation (FVT, multi-word tokenization, in-place BPE expansion) often picks merges by frequency. Frequency overweights common inputs and underweights rarer but expensive outputs. VocabX scores candidates by estimated cost/time saved, weighting fields differently (system / user / response).

It works on two layers under one criterion:

  • Sub-word — rebuild how domain words are cut
  • Macros — whole repeated spans (lines, JSON structures) as single tokens

Multiple “miners” find different repetition patterns; structural/punctuation spans mattered most in their corpora. Sparse candidates need statistical estimates so sample-based selection does not zero-out rare-but-valuable merges.

  • Cap vocabulary size; unused rows still move memory every step.
  • A/B train with identical data/seed and measure wall-clock cost under your real server (for example vLLM), not only theoretical FLOPs.

Chip peak FLOPs have grown roughly six-thousand-fold over two decades. Workloads have not gotten six-thousand-fold faster. Accelerators often sit idle waiting on data. That gap between rising compute and slower-growing memory bandwidth is the memory wall—and it explains why “twice the FLOPs” rarely means twice the tokens per second.

Arithmetic intensity and the roofline

Arithmetic intensity is FLOPs performed per byte moved from memory. High intensity → compute-bound (you can use the chip’s math). Low intensity → memory-bound (you starve for bandwidth).

The roofline model plots intensity against attainable performance. Hardware defines a ridge point: peak FLOPs divided by peak memory bandwidth. On a B200-class GPU, example specs (~2.25 PFLOP/s and ~8 TB/s) put the ridge near ~281 FLOPs/byte. Workloads left of the ridge are memory-bound; right of it, compute-bound. Extra FLOPs help only if you are on the compute side—or if you raise intensity enough to move toward the ridge.

Prefill vs decode on the roofline

In LLM serving, prefill (processing the prompt, building KV cache) does large GEMMs and often sits in the compute-bound region (high intensity). Decode (one token at a time at small batch) repeatedly reads large weights for little math per byte—intensity can be ~1 FLOP/byte, deep in the memory-bound regime. Throwing more compute at decode without fixing data movement barely helps.

Batching (including continuous batching in engines like vLLM) raises intensity by reusing the same loaded weights across many concurrent generations—moving decode toward the ridge without changing the chip.

Before buying hardware, estimate intensity, read peak FLOPs and bandwidth from the spec sheet, and place the workload on a roofline. That tells you whether to chase compute, bandwidth, batching, or quantization.

Why one GPU is not enough

Trillion-parameter-class models can need on the order of terabytes just for weights; top GPUs hold a few hundred GB. Production also needs room for the KV cache (growing with conversation) and throughput for many concurrent users. Distributed inference splits the load.

Common strategies:

  • Data parallelism — full model replicas; route requests by load or warm cache. No cross-replica math coordination.
  • Pipeline parallelism — shard by layers across GPUs (assembly line). Keep requests flowing so stages stay busy.
  • Tensor parallelism — shard within each layer; GPUs compute partial results and combine via collectives every layer. Needs high-bandwidth, low-latency interconnect inside a server; slow networks become the bottleneck.
  • Expert parallelism (MoE) — spread experts across GPUs; routers send tokens to a few experts per layer. Less compute per token, more network chatter for dispatch/combine.
  • Prefill/decode disaggregation — separate GPU pools optimized for compute-bound prefill vs memory-bound decode, with a fast KV-cache handoff. Worth it only if the interconnect can move cache quickly; plain Ethernet often is not enough.

Real systems stack these (multi-dimensional parallelism) under an orchestration layer for routing, load balance, and failure handling. The memory wall tells you why decode hurts; parallelism tells you how production serving escapes a single device.

Training a frontier model can cost hundreds of millions of dollars and months of work. Afterward the model is a static pile of weights sitting in memory. It does nothing until inference runs those weights against new inputs to produce outputs. Chatbots, coding assistants, and agents are almost entirely inference products. Training happens once; inference happens on every request—and over time inference cost usually dominates.

Inference engines

An inference engine turns weights into a reliable serving system: scheduling requests, managing accelerators, batching work. Examples include vLLM, Ollama, and llama.cpp. Many expose OpenAI-compatible endpoints so applications can swap models without rewriting clients.

Before the data center, text becomes tokens—words, subwords, punctuation mapped to IDs. The model never sees characters; it sees ID streams. Tokenization is cheap computationally but defines billable prompt size. Larger vocabularies can pack text into fewer tokens but add training overhead.

Inside the facility, requests are authenticated, then routed by prompt length and content to suitable hardware. Serving each request alone wastes GPU capacity—like firing an industrial oven for one pastry. Batching groups requests; continuous batching slots a new request in as soon as another finishes so utilization stays high.

Prefill and decode

LLM inference has two phases with different bottlenecks.

Prefill reads the whole prompt at once and builds the KV cache—working memory of what has been processed so far. Without it, every new token would force reprocessing the entire conversation. Prefill is compute-bound: large parallel math, limited by peak FLOPs.

Decode generates the reply one token at a time. Each step runs a forward pass, produces a distribution over the vocabulary, samples or picks a token, appends it, and repeats—always consulting the growing KV cache. Decode is memory-bandwidth-bound: limited by how fast weights and cache move from memory, not by raw math throughput.

Two latency metrics map to these phases:

  • Time to first token (TTFT) — mostly prefill cost (how long until the user sees the first piece of the answer).
  • Inter-token latency (ITL) — time between subsequent tokens (decode step cost).

Together they largely define perceived LLM latency.

Why this matters for products

Prefill wants compute; decode wants fast memory. Optimizations that help one phase may not help the other. Batching often raises arithmetic intensity in decode by reusing loaded weights across many users. Quantization shrinks what must be moved. Local vs. cluster engines differ in how far they push continuous batching, paged KV caches, and multi-GPU parallelism—but the prefill/decode split is the mental model underneath all of them.

Inference is the machinery between a trained model and something people can use in real time. Understanding its phases is how you know what to optimize next.

Cost and product implications

Because decode is bandwidth-heavy, product latency budgets should track ITL under realistic concurrency, not only single-stream demos. Prefill-heavy apps (long documents) stress FLOPs and TTFT; chatty multi-turn agents stress KV-cache growth and memory. Quantization, batching, and cache-aware scheduling are levers on different sides of that split—pick them based on which phase your traffic actually pays for.

A trained model is a vast collection of weights and activations—dials tuned during training. Frontier and open models may have tens of billions to trillions of parameters. How many bits you store per parameter decides memory, bandwidth, and often speed. Quantization stores those numbers at lower precision so the same model fits smaller devices and cheaper GPUs with limited accuracy loss.

Why precision dominates footprint

Many models ship in FP16 or BF16: 16 bits (two bytes) per parameter. A 70-billion-parameter model at FP16 needs on the order of 140 GB—more than many single accelerators hold. Cutting bits is not as simple as deleting digits: floating-point layouts encode sign, magnitude, and fraction separately. Chopping the wrong bits destroys the value. Quantization maps a layer’s value range onto a smaller discrete set (for example int8 or int4), scaling and rounding consistently so values can be restored approximately at use time.

Rough storage for that 70B example:

| Format | Bits | Approx. weight storage | |--------|------|-------------------------| | FP16 / BF16 | 16 | ~140 GB | | FP8 / int8 | 8 | ~70 GB | | int4 | 4 | ~35 GB |

Model cards often encode this in names (for example 8B parameters at FP8, or weights at 8-bit with activations still at 16-bit).

The accuracy trade-off

Lower precision is like increasing pixelation in a photo: eventually meaning blurs. Int8 commonly preserves most accuracy while improving latency and fit. Int4 is a steeper cut; accuracy risk rises (often on the order of tenths of a percent to about a percent in well-done mappings, with models typically staying above ~90% of original accuracy—but “well-done” matters). Aggressive quantization needs careful calibration of scales and rounding per layer.

PTQ vs QAT

Quantization can enter at two points:

  • Post-training quantization (PTQ) — compress a fully trained model afterward. Fast and common in production.
  • Quantization-aware training (QAT) — simulate lower precision during training so the model adapts to quantization noise. Costlier in time and compute, but often holds up better at aggressive levels such as int4, where PTQ is more likely to lose accuracy.

Where it shows up

Quantization is one of the simplest, most widely used compression levers: phones, edge devices, and large inference clusters all rely on it. Local engines such as llama.cpp lean heavily on quantized GGUF packs so consumer hardware can run models that would otherwise demand data-center GPUs. Serving stacks still benefit when weights and KV-cache pressure shrink.

The practical question is not whether to quantize, but how far: choose the precision your task can afford, verify on your evals, and prefer QAT when int4-class compression must stay close to full-precision quality.

Reading precision in the wild

Production cards often mix precisions: weights at int8 or int4 while activations stay wider, or FP8 for both. Naming conventions encode that split. For local GGUF packs, choose a quant level your eval suite can tolerate on your tasks—coding and extraction can be more sensitive to aggressive quants than casual chat. Always separate “fits in VRAM” from “passes quality gates.”

You have a correct PyTorch model and you want it faster. One line—model = torch.compile(model)—wraps it. The first run may be slower while compilation happens; later runs may be faster. Compilation is an opportunity, not a guarantee, and it does not always fuse the entire model into one graph.

Three stages behind the one-liner

1. Dynamo Dynamo traces Python execution and captures tensor ops it can represent as an FX graph, along with guards: assumptions about shapes, dtypes, and state under which the compiled artifact is valid. On later calls, PyTorch checks guards before reuse; if they fail, it may recompile.

2. AOT Autograd This stage prepares the graph for the backend: decomposing higher-level ops into forms the compiler understands (sometimes expanding one op into several). For training it also captures backward graphs so both directions can be optimized. Inference skips backward capture.

3. Inductor The default backend generates code for the target: fusing compatible ops, scheduling work, reducing intermediate memory traffic. On GPUs it often emits Triton kernels; on CPUs, C++. Large matmuls may still call specialized libraries. The goal is efficient execution, not minimizing kernel count for its own sake.

Without compile, Python dispatches ops one by one; small ops pay launch and intermediate-data overhead. Compile lets PyTorch optimize across ops that would otherwise run separately.

Graph breaks: when capture stops

If Dynamo hits code it cannot capture—for example a Python branch on a tensor value, or certain .item() uses—it finalizes the graph so far, runs the unsupported bit in eager Python, then resumes tracing. The program can still be correct, but you get smaller regions, fewer fusion chances, and overhead at boundaries. Setting fullgraph=True requires a single graph and errors on breaks—useful when you want failures to be loud.

Disappointing speedups? Check graph breaks first: did you capture enough of the model?

Two separate costs of .item()

Reading a scalar from a tensor into a Python value (for an if, a print, or a log) feels free. On a compiled, accelerator-backed model it can hurt in two distinct ways people often conflate:

  1. Graph break — the compiler cannot treat the surrounding region as one piece; you get two smaller regions with Python in the middle, so fuse/reorder/memory planning across the whole stretch is limited.
  2. Synchronization — to hand Python that number now, the host waits for the accelerator to finish computing it. While the host decides what to do next, the chip may sit with an empty queue. That idle gap is real wall time, separate from the graph-break mechanics.

A print or log that pulls a scalar does the same class of interruption as an obvious if tensor.item() > threshold.

Measuring honestly

First-call compile cost should not be mixed with steady-state latency. Changing shapes can force recompilation; dynamic-shape support reduces some of that but not all specialization. On GPUs, synchronize properly so you time completed work, not just kernel launches.

When compile does not help, ask: Did we capture enough? Are graph breaks limiting fusion? Are inputs forcing recompiles? Are we measuring compile time or steady state? Those questions beat celebrating that the model was “compiled.”

Definition: feedstock, factories, and goodput

AI factory. Most AI efficiency work optimizes algorithms or GPU kernels. Naveen Rao (Unconventional AI) argues the deeper limit is the physical substrate of computation—and that brains are an existence proof the industry underweights. The teaching frame is intelligence per watt: useful cognition delivered per unit energy, not FLOPS marketed on a slide. Digital accelerators improved cost and packaging faster than true energy per useful operation once memory traffic is counted. If AGI-scale ambition collides with the grid, substrate becomes strategy.

The energy wall

Human brains run on roughly 20W each. Aggregate that across humanity and you get on the order of ~160GW of biological compute—set against global electrical capacity measured in thousands of gigawatts, with AI training and inference racing to claim an alarming share. Rao’s point is not a precise forecast of blackouts; it is that energy, not ideas, becomes the binding constraint within a few years if trajectories continue.

Biology’s gap versus machines is not a rounding error. A macaque brain is probably under a watt; complex mammalian and insect behaviors run on milliwatts. A phone is about a watt; a squirrel leaping branch to branch may run on less than 10mW—on the order of 1/100 of that phone—while solving perception and control problems we still struggle to match with much larger computers. Tokens-per-second favor machines; discovery-grade intelligence still looks expensive in joules.

Thermodynamic and lithographic bounds

There is a physical asymptote: the Landauer principle bounds how much irreversible computation you can buy per unit energy. Biology sits high on the efficiency curve after billions of years of evolution, yet Rao places it still perhaps ~100× (an order or two of magnitude) short of that thermodynamic limit. Modern digital practice sits far lower. Limits of 2D lithography define another ceiling for conventional chips. Focused effort might push toward lithography’s edge—still, in his sketch, something like three orders of magnitude better than where we are today on energy efficiency—and still short of biology’s neighborhood, let alone Landauer.

Crucially, advertised FP8 flop efficiency has not moved like sticker prices: manufacturing and packaging got cheaper; energy per flop with memory access improved only incrementally. That is why “buy more GPUs” is a cost story that eventually becomes a physics story.

Mechanism: non-von Neumann dynamics

Brains do not primarily compute by matrix math on a von Neumann shuttle between memory and ALU. They use nonlinear dynamics: time-varying interactions among neurons are the compute. The systems are stochastic; they are not brittle one-and-zero machines where a single bit flip voids the program.

Rao’s engineering direction: trainable coupled oscillators and related dynamical circuits. Classic Kuramoto synchronization shows rigidly coupled oscillators converging regardless of start state. Generalize to a trainable coupling fabric and the system can traverse rich state-space trajectories. Training becomes steering those trajectories—not endlessly writing tensors out, operating, and writing back. In his demo framing, physics runs after an initial condition (and optional early error signal); state is implicit in the evolving system. Energy burns less on memory traffic because state and function overlap.

This is truly non-von Neumann relative to CPUs (fast single-thread memory loops), GPUs (wide operand batches still crossing memory), and even compute-in-memory designs that still largely linearize time. Unconventional’s claim is not that GPUs stop mattering tomorrow, but that ASI-level abundance likely needs a different abstraction than 1940s digital floating-point machines adapted to other workloads.

Startup advantage, in his telling, is lack of baggage: months from no team to prototype tapeout cycles versus incumbent roadmaps—accelerated by using AI in the design loop itself.

Why builders should care now

Even if you never fabricate oscillators:

  • Make energy per task a first-class KPI alongside latency and quality.
  • Expect co-design between models and machines to intensify; architectures that assume infinite HBM movement will age poorly.
  • Plan products and margins for a world where “just scale the cluster” collides with power delivery, not only chip supply.
  • Watch substrate research as option value: the winners of the next decade may own different primitives than CUDA comfort suggests.

Failure modes

  • Confusing cheaper tokens with thermodynamic progress.
  • Ignoring memory movement when quoting efficiency.
  • Betting entire roadmaps on unbounded digital scale without power, cooling, and siting plans.
  • Dismissing biology as metaphor only—then being surprised when efficiency gaps dominate unit economics.
  • Overclaiming near-term replacement of GPUs; the honest stance is parallel research, not instant substitution.

Practice checklist

  • Report joules (or watts × time) per successful task in internal dashboards
  • Separate algorithmic wins from packaging/cost wins in efficiency reviews
  • Include power and interconnect constraints in capacity planning, not only GPU counts
  • Prefer model/serving designs that reduce memory traffic for the same quality
  • Track substrate and unconventional-compute research as strategic awareness, not only vendor roadmaps
  • Avoid demo metrics that hide energy (e.g., quality at unlimited batching power)
  • When evaluating infra vendors, ask about energy per useful operation with memory, not peak FLOPS alone

Agents that call enterprise APIs as a shared application identity break three things at once: audit trails (who did this?), user-level authorization (what may this user do?), and least privilege. Production agents need identity that answers two questions on every call: which agent acted, and for which user.

Why “service account for everything” fails

If the CRM or ticketing API only ever sees the agent platform’s client credentials:

  • Every action looks like the same principal.
  • Downstream ACLs cannot enforce per-user permissions.
  • Prompt injection or buggy tool choice can act with the platform’s full power.

User OAuth tokens stuffed into the agent as long-lived secrets are also weak: the tool may not distinguish agent from human, and stolen tokens last weeks.

On-behalf-of (OBO) token exchange

OBO bridges two audiences. The user authenticates to the agent app and receives a JWT for that app. Downstream APIs expect a token whose audience is their API connector. A gateway in the middle:

  1. Accepts the inbound JWT (agent audience).
  2. Calls the IdP token endpoint with requested_token_use: on_behalf_of, client credentials, and the target scope.
  3. Receives a new token that preserves the user’s claims but targets the downstream API.
  4. Invokes the API; the API maps claims (for example preferred_username) to a local user and applies that user’s permissions.

Configure exchange on the gateway target so it happens on each request—application code should not reinvent token plumbing per tool. Pair with input/output guardrails so identity propagation is not the only safety layer.

This pattern generalizes beyond any one SaaS: any OAuth-protected REST API can sit behind the same exchange.

Stronger still: agent identity as a first-class principal

Beyond OBO, treat agents like privileged machine identities:

  • Registry — catalog approved agents, MCP servers, and skills; gate discoverability with approval workflows.
  • Per-agent credentials — each agent gets its own identity checked on every request; no orphaned actions.
  • Delegation assertions — users authorize agents without sharing passwords; audience-scoped tokens limit blast radius if one token leaks.
  • Revocation — real-time status checks (for example OCSP for X.509) so compromised agent certs stop working immediately.

MCP itself is transport-agnostic and does not define authentication. Without identity mechanisms on top, any component can impersonate an agent, replay credentials, or invoke tools without authorization. Signed request envelopes and proof-of-possession close that gap for high-assurance deployments.

Practical rules

  • Never put tenant/user identity in LLM-visible tool arguments.
  • Prefer short-lived tokens and vault-issued session credentials over shared API keys.
  • Log both agent identity and user identity on every tool call.
  • Deny by default; subscribe agents to tool groups explicitly.

Takeaway

Propagate the user with OBO (or equivalent delegation); identify the agent as its own principal; keep credentials short-lived and out of the model’s reach. Audit and least privilege only work when both identities travel with the request.

Precise rules (“block sign-in before sharing mailbox”) can be checked with automated reasoning / policy proofs across paths. Soft expectations (“friendly tone”) cannot—limit access, evaluate behavior, and escalate ambiguity to humans. Widen autonomy as evidence accumulates.

Enforce limits outside the model

Never rely on the agent to police itself. Put policy on the tool gateway so checks hold when reasoning fails. Temporal policies can require prerequisite steps in a session before later tools unlock. Content guardrails filter what the agent says and is told; sandboxes limit filesystem/network reach from development through production.

Catalog agents and MCP servers in a registry with approval workflows so shadow agents do not appear. Issue per-agent identity on every request.

Evaluation bias: your scoreboard may be lying

Trust also fails when metrics are circular. One team found 96.8% of “ground truth” labels were the incumbent model’s own predictions. Alternatives looked worse by construction. Labels also contained errors and out-of-spec categories.

Repair pattern

  • Fresh expert annotations with no access to incumbent outputs.
  • Multi-label where reality is multi-label (penalizing reasonable secondary labels was fake ambiguity).
  • Metrics that match the business (Micro F1 for overall correctness, Macro F1 for rare classes, per-label precision/recall).
  • Prompt/model optimization only after unbiased ground truth exists—treat prompt versions like an RL loop with error analysis as the gradient.
  • Report cost and quality together; unbiased eval unlocked both higher accuracy and large cost cuts in the published case.

Production agent eval frameworks should score faithfulness, tool choice, and regressions continuously—not only at launch.

Enterprises want AI that is smart, fast, and secure. Like musical chairs with too few seats, you often get only two. That three-way tension is the AI security trilemma.

Why only two chairs?

Smart means stronger reasoning, larger context, tools, autonomy, and permissions—the same ingredients that expand attack surface. Speed means low latency and autonomous action—less time to scan inputs, catch prompt injection, inspect outputs, or enforce policy. Security means injection defenses, output validation, DLP, access control, sandboxing, logging, and human oversight—each adding friction that slows the system.

Capability increases attack surface: memory, internet, tools, databases, APIs, sensors, and actuators are each a pathway. Perfect security everywhere tends to make the system dramatically slower. Perfect speed and autonomy tend to skip inspection.

Picking two on purpose

  • Smart + secure (accept slow) — deep research, careful medical image analysis: twenty minutes of thoroughness beats twenty seconds of risk.
  • Smart + speedy (accept risk) — public data, low-impact PoCs, outputs that do not trigger high-stakes actions.
  • Secure + speedy (accept “dumb”) — narrow tasks (home automation that toggles lights): small models, tight permissions, fast responses.

The mistake is pretending you got all three without an architecture that pays for the third somewhere else.

A security proxy as an “extra chair”

One balancing pattern is an AI security proxy: a policy layer outside the model that inspects inputs, sanitizes outputs, gates tool permissions, and applies uniform controls. The model can stay relatively smart and fast while enforcement lives in the wrapping—similar in spirit to harness-level guardrails. It does not erase the trilemma, but it stops forcing every control into the model’s critical path.

OWASP LLM risks in the agent era

The OWASP Top 10 for LLM applications remains a shared language for AI risk—not a compliance checkbox. Prompt injection and sensitive information disclosure stay near the top; excessive agency has climbed as systems move from generating text to taking actions. Long-context benchmarks often ask whether a model “remembers” something far back in a document. That question hides several different skills. State tracking—following how entities change as a document unfolds—has its own difficulty ladder. Treating every state-tracking failure as “the context window was too short” misdiagnoses both architecture and training.

Four levels of difficulty

AllenAI’s StateBench organizes state tracking into four theoretically motivated levels, easiest to hardest:

| Level | Intuition | Code analogy | |-------|-----------|--------------| | R-trivial | Value never changes; recover the first assignment | let x = 4 | | Aperiodic | Latest write wins; earlier values can be ignored | x = 4 then later x = 2 | | Soluble | Updates depend on the current value | x = x + 5 | | General finite | Assignment by reference; variables depend on each other | x = y, swaps |

The hardest level resembles following cups as a magician swaps them: miss one swap and the final location is wrong. Theory predicts transformers handle the easier levels better than hard dependency chains; recurrent/hybrid designs with flexible running memory (for example Gated DeltaNet) can in principle cover all four.

What evaluations show

On pretrained open models, accuracy is often high on r-trivial, drops with length on aperiodic problems, and sits near chance on general finite problems. Problem format matters: the same underlying task can look easy in one framing (RULER-style) and near chance as spreadsheet edits. Frontier models do well on r-trivial and aperiodic work, then collapse on long soluble/general sequences (reported accuracy falling to ~13% or lower on the longest hard cases).

When small models are trained directly on StateBench and tested far beyond training length, architectures diverge: Gated DeltaNet and hybrids generalize far on the easier three levels; transformers degrade on long sequences and never learn the hardest level even with direct training. For hybrids, pretrained failure can be a training-data problem; for transformers on general finite tracking, it looks more architectural.

Practices worth taking away

  • Split “needle in a haystack” retrieval from chain-sensitive state updates when designing evals.
  • Score the same logical problem in multiple formats—format artifacts can dominate architecture claims.
  • When picking long-context models for code, stories, or multi-entity workflows, ask which level of state update your product actually needs.
  • Recurrent/hybrid memory is not marketing fluff for hard state tracking; validate with level-stratified tests, not a single aggregate long-context score.

  • A chain of command clarifies which instructions win when OpenAI policy, developer system prompts, and user requests disagree.
  • Consider context carefully tells models how conversations, memories, and other evidence should inform intent without inventing preferences.
  • Defaults for supporting agency, following social norms, and controlling side effects capture subtle failure modes: over-helping that deskills users, ignoring third parties, or optimizing the asked metric while creating hidden costs.

Retire what should be personal preference

Detailed style guides age poorly and fight user taste. Prefer adaptive style driven by feedback and context, while keeping stronger defaults such as approaching questions objectively—users can request a perspective, but the model should not infer one just to please.

Train for reasons, not only rules

The Spec describes target behavior; models do not fully embody it yet. Training research aims for models that do the right things for the right reasons—understanding why principles exist so they generalize to unfamiliar situations. Public Specs invite disagreement on balances and omissions; that feedback loop is part of the method.

For builders: write your own agent policy as values → firm boundaries → overridable defaults → examples. If your “constitution” is mostly tone tips, you have not specified judgment.

Most AI you use today is a text generator: a large language model (LLM) emits tokens one at a time—sometimes with a visible chain of thought that feels like slow, deliberate “system two” reasoning. Many software decisions are not that. They are fast judgment calls: Is this email a refund request? Which team owns it? How urgent is it? That is closer to Kahneman’s system one—quick, automatic classification—than to writing a carefully argued reply.

Jev (from TypeSafe) is an example of a system-one style model: it does not write prose. It answers by selecting among options you supply and returning calibrated probabilities for each answer. That design fits structured workflows where speed, cost, and a usable confidence signal matter more than fluent text.

What the model takes and returns

You give Jev two kinds of input: state (the data the decision is about—for example a support email plus recent charges) and questions typed for discrete outcomes. Questions can be yes/no (boolean), a choice from a fixed list (team = billing | technical | sales), or a score on a scale (urgency from low to critical). Multiple questions can go in one request; answers come back together as probabilities, not as generated JSON tokens.

Because the model never has to sample a long token sequence, these calls can be faster and cheaper than asking an LLM the same structured questions. The output is also software-friendly: refund: 0.9, team.billing: 0.85, and so on. Choices are constrained to the options you provided—the model cannot invent a fourth team.

Why LLM “confidence” is a weak substitute

A common automation pattern is: send the email to an LLM, ask for structured JSON, parse the fields. That often works for labels, but the model’s self-reported confidence rarely matches true likelihoods. RLHF (reinforcement learning from human feedback) trains chat models to produce answers people prefer—and people prefer answers that sound sure. Models can therefore learn confident tone even when wrong.

Other post-training paths help differently. RLVR (reinforcement learning with verifiable rewards) scores whether math is correct or tests pass; it rewards right finals, not well-calibrated uncertainty, and reasoning traces still cost latency and money. Jev is described as trained with RLCD—reinforcement learning for calibrated decisions: the model emits probabilities and is rewarded when those probabilities match outcomes. Calibration means that when the model says “80%,” it is right about 80% of the time over a large set of comparable cases—not that any single call is proven correct.

Thresholds: automate, escalate, or ignore

Calibrated scores become operational when you attach thresholds in code. Example for a refund boolean:

  • Above ~0.9 → treat as refund; enqueue for processing.
  • Between roughly 0.1 and 0.9 → escalate to a human.
  • Below ~0.1 → not a refund; continue without that path.

The threshold encodes risk: the more a false automatic action costs, the higher you set the bar. Because scores are calibrated, the threshold also implies roughly how often the automatic path will be wrong. The same pattern can guardrail chatbots (for example scoring jailbreak likelihood on inbound/outbound messages) or sit on high-volume paths where an LLM would be too slow or expensive—every log line, every database row—echoing Jevons’ paradox: when judgment becomes cheap, it can show up in more places.

Limits and the hybrid with system-two LLMs

System-one models are not a wholesale replacement for LLMs. Current Jev-class tools take text only, struggle with math and counting, and—like any model reading untrusted content—can be steered by instructions hidden in the data. They also output confidence without an explanation: probability is not a chain of evidence.

A practical architecture pairs the two modes the way humans often do. Use system one for fast sorting and gating (is this a refund? which queue?). Use a system-two LLM for generative work that needs deliberation (draft the customer reply). Feed later customer messages back through the decision model for the next quick classification. Break big decisions into smaller audited questions so each probability lands in an observable workflow step rather than one opaque “contain this host at 97%” leap.

Treat the decision component as powerful automation with known failure modes: wrap it with input validation, independent signals, logging, drift detection, and human escalation for high-stakes outcomes. Use calibrated probabilities to route work—not as proof that the route is correct.

When AI generates a paragraph, a bad answer is embarrassing. When AI denies a loan, contains a host, or pays an invoice, a bad answer is an incident. The hard question is not only “can AI decide?” but “how do we know when it decided wrong—and whether someone made it wrong?”

Confidence is not explanation

Decision-oriented models (discussed in industry under names like Jev) optimize for structured choices and calibrated probabilities rather than long text. That is powerful for automation: software gets contain_host: 97% instead of a paragraph to parse. Probabilities report model confidence given inputs, not proof, provenance, or immunity to poisoned logs and metadata. “Garbage in, confident garbage out” still applies—and subtle drift (1% more approvals of the bad case) may look reasonable decision-by-decision while the system is compromised.

LLMs at least emit inspectable text you can challenge, tool-trace, or cross-check with another model. Pure decision black boxes need observability by design: break one big question into smaller audited steps (authorized? evidence? risk?), log inputs and outputs, validate types, watch for behavioral drift, and keep independent signals—not a single feed the attacker can tweak. Treat the decision model as an untrusted component wrapped in controls. Verify, then trust.

Agents vs rules (and when not to use AI)

Business rules are deterministic: if order age &lt; 30 days and not final sale, approve refund. Same inputs, same outputs; the firing condition is the explanation—ideal for audits, unit tests, and zero inference cost. Agents are probabilistic: they sample from likely actions given goals, context, and tools. They handle messy text, photos, and unanticipated cases rules never encoded—and they can disagree with themselves across runs.

Agents have not replaced rules. Strong systems run rules first for clear approve/deny, escalate ambiguous or unstructured cases to agents, then apply deterministic guardrails and human review above risk thresholds.

A wider palette:

  • Humans — high stakes, ethics, liability, deep ambiguity.
  • Rules/code — stable explicit logic, payments, access control, validation.
  • Classical ML — patterns in structured data (fraud, churn, demand) when rules rot.
  • Generative AI / agents — unstructured inputs, synthesis, flexible workflows where some error is tolerable.

The most important AI skill is knowing when not to use it. Hybrid stacks beat “agents everywhere.”

Human-in-the-loop is not governance

Saying “a human reviews it” is not the same as a governed system. Ask what the human can see and stop. Map trust properties to system properties: transparency of training/data choices; explainability of this output; observability as conditions change (critical for agents); what the model was optimized for; robustness to tampering. Humans uniquely read circumstances, not only features—social and ethical judgment that models do not replicate. Warm bodies without visibility, authority, metrics, and feedback loops are theater.

Risk shapes architecture; management systems sustain it

Build order should be: risk → requirements → architecture, not “ship then bolt on oversight.” Explainability that is fine for a movie recommendation (“because you watched X”) is inadequate for clinical triage, which needs lineage, provenance, and contestable traces. Baseline / enhanced / vigilant rigor should track stakes.

Organizationally, standards such as ISO 42001 frame an AI management system (plan–do–check–act across data, model, system, and usage risk), complementary to NIST’s voluntary AI RMF guidance and binding regimes like the EU AI Act. Checkbox governance fails; continuous management lets teams scale AI without locking the organization in the trunk of an unaccountable model.

Getting one agent to call a model and a few tools is not the production problem. The production problem is how many teams can ship agents inside the same security, cost, and quality boundary—without every team reinventing gateways, identity, evals, and rollback.

Three operating models

Enterprises usually land in one of three shapes:

  • Centralized — One AI/ML team builds every agent. Controls stay consistent; that team becomes the bottleneck.
  • Decentralized — Each business unit builds alone. Speed goes up; standards, cost visibility, and audit trails drift.
  • Federated — A platform team owns shared, governed services; domain (“workstream”) teams own prompts, tools, data, and SLOs. Most mature programs end here.

The unit of scale in a federated design is not “an agent.” It is a workstream cell: an isolated boundary with its own runtime, memory, tool gateway, budgets, tags, and pipeline. One cell can deploy, fail, roll back, or retire without coordinating another team’s release.

What every workstream needs on the paved road

Treat these as platform product requirements, not optional tooling:

  1. Governed model access — Untrusted inference goes through an approved gateway that applies guardrails, model/region allow-lists, rate limits, and token budgets.
  2. Governed tool access — Agents discover and invoke only approved tools through an authenticated MCP (or equivalent) gateway with least-privilege roles and an auditable owner.
  3. Short-lived workload identity — Inference and tool calls carry identity that expires; shared long-lived service keys are a failure mode.
  4. Isolated runtime and memory — Session isolation (for example microVM-per-session) so one tenant or user cannot bleed into another.
  5. Evaluation-gated promotion — Deploy to non-prod, run quality and adversarial denial probes (unapproved model, unsubscribed tool, cross-account identity), then human-approve with evidence—not a green unit-test badge alone.
  6. Cost attribution and fleet ops — Logs, traces, quotas, and chargeback by team without giving central operators write access to every workload.

Separate inference gateway from tool gateway

Collapsing “talk to the model” and “call the CRM” into one path mixes two different trust and cost problems. Keep them distinct:

  • Inference gateway: model admission, guardrails, routing, token budgets.
  • Tool gateway: registry-approved aliases, policy evaluation, outbound credentials.

Platform owns admission of models, guardrails, and registry records. Workstreams own application behavior inside those contracts. Direct developer deploys that bypass the reviewed pipeline defeat the model.

Lifecycle you can prove

A production platform should demonstrate, with tests, that:

  • An approved model call succeeds and an unapproved model/region is denied.
  • A subscribed tool call succeeds and an out-of-subscription call fails as designed.
  • Cross-cell identity is rejected.
  • The previous runtime version can be restored.
  • Retirement revokes grants, then tear down gateway, runtime, and memory in dependency order with zero residual resources.

If you cannot show those paths, you have a demo environment—not a platform.

Takeaway

Agent platforms succeed when the platform product (templates, gateways, identity, eval gates, cost tags) is versioned and self-service, and domain teams only customize inside that contract. Federate ownership of agents; centralize the controls that must not drift.

Build a foundation, not a one-off feature

Regulated SaaS teams that skip straight to “one assistant” rebuild isolation for every subsequent feature. Invert the plan: ship a horizontal foundation first (embeddings, per-tenant indexes, execution isolation, guardrails), then cut vertical use cases into it. Teams report large cuts in per-use-case deployment time once the foundation exists.

  1. The AI system is not the source of truth for complex, source-specific permission models (inheritance, groups, denies).

  3. Upstream permission features evolve; connectors lag and create gaps.

  • Stage 1 — Pre-filter with cached ACL attributes so you do not call the source API for every document in the corpus.
  • Stage 2 — Real-time verify candidate docs against the authoritative API (SharePoint, Google Drive, Confluence, …) with the user’s identity before passages enter the LLM context.

Always-current permissions, confidence to scale coverage, less dependence on sync frequency. Pair with grounding checks and content filters for responsible generation.

Evidence for auditors

“The model decided” does not survive compliance review. Keep OpenTelemetry traces of retrievals and tool calls, per-tenant invocation logs, and cached briefs with TTLs. Attribute cost and access to the initiating tenant/user.

Takeaway

Isolate tenants below the application layer; treat uploads as hostile; verify document permissions with the system of record at query time after a cheap pre-filter. Security is part of the AI foundation, not a feature flag on the chatbot.

Four control questions

Convenience does not guarantee security, trust, resilience, or accountability—you would not paste company secrets into a random chatbot and assume no harm. Customers, regulators, auditors, and boards increasingly expect demonstrable control. With a software foundation that encodes these questions into architecture, sovereignty lets teams move faster because systems remain governed and accountable.

When sovereignty is an architectural priority, the answer to “who is in control?” should be simple: you are—of information, of where and how it runs, of the stack, and of the intelligence you deploy.

Residency vs sovereignty vs localization (practical distinction)

Teams often conflate three related ideas. Residency is physical location of stored bytes. Sovereignty is which legal authority can compel disclosure or constrain processing. Localization is a mandate that storage and processing stay inside a boundary. Cloud makes all three sticky: a U.S.-owned provider operating a German region may put residency in the EU while contractual and extraterritorial claims remain contested. Agentic workflows worsen opacity because tool calls and model APIs can silently move intermediate representations across borders. Enforceable placement controls—and legal sign-off on the architecture—belong in the design, not as a post-deployment surprise.

The data that makes AI most useful is often the data that can hurt you most: customer PII, health records, financial details, contracts, credentials. Organizations spent decades building controls so humans would not mishandle that information. AI changes the tempo. Models and agents can read, transform, and move data at machine speed, so the controls around them must operate at machine speed too.

There is a false choice many teams feel: either feed the crown jewels to the model and get sharp answers, or starve it and get bland, generic output. A third path exists—useful outcomes without uncontrolled exposure—but it rests on five foundational capabilities.

You cannot protect what you cannot see

Most enterprises lack a single view of where sensitive and regulated data lives. That is not only a storage problem. Data is the lifeblood of AI; it circulates. It sits on premises, on endpoints, in SaaS and cloud systems, and in transit across networks. Visibility means knowing where it is, how it moves, who (or which workload) uses it, and why.

Without that map, every AI project is a bet placed in the dark. Shadow AI—employees pasting documents into public chatbots—makes the map incomplete in a different way: exposure starts where governance never looked.

Classify before the model consumes

Seeing data is not the same as understanding it. Classification by sensitivity level has to happen before AI consumption, not as a post-incident cleanup. Manual tagging is slow, incomplete, and drifts as data arrives and leaves continuously. Automated classification that reads content and assigns sensitivity—and runs early and often—is what keeps controls matched to value.

Too much control kills innovation and budget. Too little invites fines and broken trust. The balance is only possible when sensitivity is known up front.

Residency, sovereignty, and localization

Location is a first-class control, not a footnote.

  • Data residency asks: where is the data physically stored?
  • Data sovereignty asks: whose laws apply to that data?
  • Data localization is the legal requirement that certain data must be stored and processed inside a country or region.

These diverge in cloud environments. A U.S. company storing data in a German data center may place residency in Germany while facing EU/GDPR obligations—and possibly conflicting claims if the cloud provider is under another jurisdiction. Processing location may differ from storage location, and cloud metadata often hides that. Organizations need enforceable controls over where data lives and how it crosses jurisdictions, with legal teams aligned to the technical design.

Identity and access: the four As

As more users, apps, and models touch sensitive data, access control becomes the boundary that keeps interactions governed. Identity and access management can be remembered as four As:

  1. Administration — provision and deprovision accounts, approvals, least privilege.
  2. Authentication — prove who (or which workload) is claiming the identity—MFA, passkeys, machine identity.
  3. Authorization — decide what that identity may do: roles, attributes, conditional access.
  4. Audit — prove the first three worked: immutable logs of movement, access, and which AI workloads used what.

Auditors and regulators need evidence, not assumptions. Rebuild lineage after the fact and you are already on the defensive. Continuous logging of data movement, retention of immutable trails, and analysis that answers where / who / what / which AI keep evidence ready.

Trustworthy AI rests on trustworthy data

Software organizations matter as much as tooling. Cross-functional programs ship products; function heads keep electrical, mechanical, and software cohesive; communities of practice share AI workflows, skills, and tooling. Edge AI without an industrial org chart is a prototype.

Autonomy with hard constraints

Autonomy appears wherever a decision must be made: perception, intent, intervention.   • Update regressions treated as surprises. Hardware + software co-evolution means every update can break perception. Budget retrain, re-certify, and field test as first-class work.

  • Prefer consecutive real-world gates over isolated sim milestones when promoting autonomy versions.

Define diffusion (vs. deployment)

Deployment is turning a model on behind a feature flag. Diffusion is changing how work actually moves: who initiates tasks, which systems get written, how exceptions are handled, and what gets measured. Levie’s prediction crystallizes the end-state: within roughly five years, a large majority of enterprise tokens may go to work no human user ever initiated—agents operating on content and workflows in the background. Why enterprises reject the AI they asked for

Torres’s framing matches what practitioners see after the pilot honeymoon:

  • Workflow mismatch. Copilots that summarize or draft without changing systems of record leave humans as the integration layer. Dashboards that still need a person to analyze and click are not AI-led operations.
  • Trust and permissions. Agents without clear audit trails, least-privilege scopes, and rollback feel like liability, not leverage—especially on contracts, money movement, and customer data.
  • Unit economics. Seat licenses plus opaque token burn without outcome pricing misalign incentives. Levie warns that lab token subsidies are temporary; buyers want model-agnostic routing rather than the fox guarding the henhouse.
  • Change management. Managers buy tools; teams protect process. “AI transformation” slides do not retire the human bottlenecks in customer experience or contracting unless incentives move.

Coding diffused fast because the verifier (tests, CI) and the artifact (code) already lived in the same loop. Legal, sales ops, IT, and CX often do not.

Reinvention patterns that work

Content → agents (Box). Levie describes sitting on enormous file estates—contracts, research, loan docs—where enterprises rarely know what is inside unless a human opens the document. The product reinvention is not a prettier file browser; it is agents that can retrieve, reason, and act on that corpus inside enterprise controls. Value sits in the bridge from raw model capability to bank/law/pharma workflow—not in owning the frontier weights.

AI-led execution (Agency). Torres pushes “deprogramming” business habits: stop designing flows that require human intervention at every step. Instruct AI to execute outreach and resolution paths; keep humans for exceptions and policy, not every ticket.

Metric flip in verticals (Crosby). Legal AI wins when it optimizes deal velocity, not billable hours. Incumbents priced on time under-serve speed and throughput; a product that shortens contracting cycles can reframe the buyer’s KPI and the seller’s packaging.

Open agent platforms inside the enterprise (Block / Goose). Prasanna’s Goose story is AI-first internal platform thinking: an open-source agent that developers and operators can extend, with the company owning the harness, tools, and governance. Diffusion accelerates when the agent is a programmable layer over real internal systems—not a sealed chatbot.

Mechanisms behind successful diffusion

  • Start from a workflow KPI (cycle time, escape rate, recovery time, deal days)—not from “AI features shipped.”
  • Narrow production scopes with logs humans can correct; widen autonomy only after measured reliability.
  • Rebuild internal platforms—identity, IT, eval harnesses, tool registries—so agents have somewhere safe to act. “Rebuild IT for AI” is infrastructure work, not a slogan.
  • Model-agnostic product surfaces that route tokens and peel off specialized models where economics or quality demand it.
  • Outcome-aligned pricing where possible; pure token passthrough rarely matches buyer value.

Failure modes

  • Feature-pack theater: chat in the sidebar, unchanged system of record.
  • Pilot islands that never connect to production identity or data residency.
  • Measuring vanity metrics (messages sent) instead of business outcomes.
  • Over-broad agents that trip security review and get banned org-wide.
  • Pricing that rewards token waste or seat sprawl.
  • Assuming coding-style diffusion timelines for domains without verifiers.

Practice checklist

  • Name one workflow KPI before writing the PRD
  • Map systems of record the agent must read/write—and permission them explicitly
  • Require audit logs and human correction paths in v1
  • Prefer outcome or workflow pricing experiments over pure seat+token bundles
  • Invest in internal agent platforms (tools, evals, identity) as shared infrastructure
  • Pilot with a team whose incentives improve if the KPI moves
  • Plan model routing so you are not locked to one lab’s meter
  • Treat change management as part of the product: training, defaults, and retirement of old steps

A shopping (or support, or triage) agent on a frontier model works—until you multiply search → read → refine → verify → decide by every user. One completed task is many billed calls. Smaller models are cheaper and faster, but usually worse at the task. Knowledge distillation transfers teacher behavior into a student so you keep much of the quality at student economics.

Sequence-level distillation (SeqKD) for agents

SeqKD is the portable end of the spectrum: the teacher generates text; the student trains with ordinary supervised fine-tuning. You need no teacher logits, weights, or RL infrastructure—so it works with API-only frontier models.

For agents, the sequence is not a paragraph. It is a trajectory: ordered reasoning, tool calls, and observations. Training on whole successful trajectories teaches multi-step behavior, not a single final answer.

Pipeline

  1. Generate — Teacher acts as the agent on training problems (sample with temperature > 0 for diversity).
  2. Reject — Keep only trajectories that a programmatic grader marks solved. A capable-but-imperfect teacher becomes a clean dataset.
  3. Encode per step — Each step is a training row: conversation so far → next reasoning + tool call. Loss on the assistant turn only; do not train the model to invent environment observations.
  4. Compress observations — Tool results dominate tokens; keep fields the next decision needs; cap results and steps so rows fit max_len.
  5. Split by problem, not by row — Otherwise near-identical steps leak across train/val.
  6. Fine-tune — LoRA or full SFT on serverless/customization infra; version the model package.
  7. Evaluate cheap then expensive — First score tool-name selection against teacher steps; then run full held-out agent loops.

Keeping teacher reasoning traces beside actions is often what carries the student most of the way toward teacher quality.

When SeqKD is the right first move

  • You have inputs but no high-quality labels (especially multi-turn tool use).
  • The teacher is closed/API-only.
  • You want a strong, cost-effective baseline before heavier RL (GRPO, multi-turn RL).

Narrow, high-value tasks (alarm triage, catalog recommend, document fields) repeatedly show specialized students beating frontier models on accuracy and cost when the pipeline from raw ops data → certified set → fine-tune → eval artifact is repeatable.

Related efficiency pattern: route, don’t always distill

Not every request needs the student or the frontier model. An adaptive stack can use a tiny local model to classify difficulty, handle routine work offline, and escalate hard work to cloud frontier models—cutting cost and latency for the common case without a distillation project.

Takeaway

Agent cost is loop cost. Distill behavior via graded teacher trajectories into a smaller student; evaluate tool selection and end-task success separately; reuse the dataset across student candidates.

Group Relative Policy Optimization (GRPO) needs many rollouts per step. Full-weight sync between a trainer and vLLM is heavy. LoRA changes the systems story: a rank-1 adapter is a few megabytes, so training and inference can live on separate machines without NCCL—if you sync adapters carefully.

Why LoRA fits RL

Policy-gradient RL often yields ~O(1) bits of useful signal per episode. Thinking Machines’ “LoRA Without Regret” argument (cited in the HF recipe) is that even rank-1 LoRA can match full fine-tuning for that regime. TRL’s AsyncGRPOTrainer (v1.14+) can train a LoRA adapter and sync only that adapter to vLLM via /v1/load_lora_adapter, writing files to a shared path rather than shipping tensors.

A Jobs + bucket architecture

A practical Hugging Face Jobs pattern:

  1. Trainer Job — AsyncGRPOTrainer + a small local proxy
  2. vLLM replica Jobs — base model + runtime LoRA, read-only mount of the same Storage Bucket
  3. Bucket — adapters, checkpoints, versioned policy directories under a shared mount (for example /lora)

The trainer publishes trl-policy-v{N} with an atomic rename; replicas load by path. Ephemeral Jobs can resume from the bucket after preemption.

Versioned adapters and staleness

max_staleness is how many policy versions a rollout may lag. If staleness is 4, vLLM must keep current + prior versions so in-flight generations finish under the correct weights. Budget enough LoRA slots (for example --max-loras 6 when staleness is 4) so a sync can load the new adapter before unloading the oldest. Versioned names matter: reusing one adapter name poisons prefix/KV cache across weight versions and can make training ratios drift silently.

Proxy duties

A proxy in front of replicas:

  • Adds Job auth headers so TRL stays unaware of HF Jobs URLs
  • Broadcasts adapter load / pause / resume to every replica
  • Routes completions so the G rollouts for one prompt share a replica’s KV prefix cache (block hashes chained and seeded with adapter name)

Round-robin wastes prefill; affinity to the replica that already holds the prompt’s blocks recovers it.

Curriculum for a sanity run

Use problems with mid-band success rates (for example 20–80%) so early reward is informative. Pin vLLM versions; treat flags and runtime LoRA endpoints as part of the recipe. Start with adapter-only sync only for configs vLLM can serve as-is (plain LoRA at or below --max-lora-rank; DoRA / modules_to_save may fall back to merged-weight sync).

Small-model GRPO for structured outputs

Separately, a light GRPO recipe on LFM2.5-350M (~500 samples, ~100 steps on a free Colab/Kaggle GPU) raised IFStruct schema-compliance from ~22.6% to ~29.7%. Same idea at tiny scale: verifiable format rewards + short RL beats hoping a base SLM invents reliable JSON/YAML.

What fine-tuning does

Start from a base LLM (frontier API or open weights) trained on broad data. Fine-tuning continues training on a narrow corpus—contracts, support tickets, house style—adjusting weights into a specialized model. It can help on narrow tasks, but it is not free: data collection, training, evaluation, regression control, and chasing a moving frontier that may obsolete your custom weights before you ship.

Why general models caught up

Three shifts reduced the need to bake knowledge into weights:

  1. Huge context windows — from a few thousand tokens toward a million-plus; large document sets can ride in the prompt.
  2. Reasoning at inference time — extended thinking can outperform stale specialized weights for many tasks.
  3. Cheaper, stronger frontier inference — the customization target moves under you.

A practical stack:

  1. Start with a strong base model.
  2. Apply prompt and context engineering.
  3. Add RAG when knowledge is fresh or proprietary (retrieve at query time instead of training it in).
  4. Add agent skills when what is missing is procedure (how to hit this SQL schema), loadable on demand by any capable model.
  5. Reach for fine-tuning only when that stack cannot clear a specific bottleneck.

When fine-tuning still wins: tight latency (voice agents that cannot wait on heavy reasoning models), distillation (teacher traces into a smaller student), and reinforcement fine-tuning when outputs can be programmatically graded. Much production “fine-tuning” is LoRA or related parameter-efficient adapters: small trainable modules atop frozen base weights.

llama.cpp vs vLLM for local serving

Running locally cuts API cost, outages/rate limits, and—often most important—keeps data on your machine. Two engines dominate different niches.

llama.cpp optimized for accessibility on consumer hardware: aggressive quantization, packing weights/tokenizer/config into portable GGUF files, and CPU as well as GPU paths—enabling laptops, Pis, offline factories/IoT. Ecosystems like Ollama and LM Studio grew on these ideas.

vLLM targets efficient serving at scale on accelerators (NVIDIA, and broader stacks): continuous batching, careful KV-cache management (paged attention), speculation, and patterns like prefill/decode disaggregation. Same OpenAI-compatible APIs many apps already use—so teams often prototype on a hosted API, then move to vLLM (or llama.cpp) when bills and privacy demand it.

Rule of thumb: llama.cpp-class tools for personal/edge and constrained hardware; vLLM-class engines for multi-user production throughput. Both can host agents and RAG; pick for hardware and concurrency, not for “which logo runs Llama.”

Related: Continual Learning, Model Collapse

Imagine each generation of students studying only the previous class’s notes, never the textbook. Errors compound until nobody remembers the original. Replace students with models, notes with synthetic content, and textbooks with human knowledge, and you have model collapse: a degenerative process where training on AI-generated data gradually erases information about the real-world distribution the first models learned from.

Research groups (including work associated with Oxford, Cambridge, and others) have shown that recursive training on synthetic outputs can make models forget rare but important information and produce more repetitive, less accurate results. Think photocopy of a photocopy: early copies look fine; late ones barely resemble the source.

Early vs late collapse

Knowledge is uneven. Common facts sit in the middle of a bell curve; rare diseases, minority languages, niche science live in the tails. Generators preferentially reproduce high-probability content, so tails compress first.

  • Early collapse — rare events fade; common patterns still look fine.
  • Late collapse — structure of reality degrades; outputs stay fluent and confident but disconnect from the original distribution.

An image-model parable: abundant dogs and cats, few albino peacocks. Each synthetic generation emits fewer peacocks until the model behaves as if they never existed. Reality did not change; the model’s representation did.

Why the risk is subtle

Collapse is not merely “AI gets worse” in an obvious way. Effects include:

  • Loss of diversity — answers converge on the average; a hall of mirrors online.
  • Knowledge collapse — fluency and confidence remain while factual grounding slips—harder to detect than blatant failure.
  • Bias amplification — small under-representation becomes structural invisibility across generations.
  • Feedback loops — as the web fills with AI text, images, code, and posts, future crawls ingest more synthetic material.

Controlled experiments verify the mechanism. Full catastrophic collapse in the wild is debated: major labs use human feedback, curation, filtering, RAG, and quality pipelines rather than raw recursive scrapes. Treat collapse as a long-term engineering hazard, not a claim that every model is already ruined.

How to stay anchored to reality

  • Keep humans in the loop — even modest amounts of authentic human data recalibrate distributions.
  • Data provenance — know what is human-created, AI-generated, or verified; break uncontrolled recursive loops.
  • High-quality synthetic data — verified, diverse, grounded, human-validated synthetic sets can help; poor synthetic data is the enemy.
  • RAG and external grounding — consult fresh sources instead of relying only on internalized patterns.
  • Multi-agent verification — evaluate accuracy, novelty, and grounding before accepting material into training pipelines.

Intelligence—biological or artificial—does not thrive in an echo chamber. The limiting factor for future AI may not be parameter count but whether we preserve a reliable link to the real world. If models mostly learn from models, the challenge is not teaching them to think—it is stopping them from forgetting what reality looks like.

LLMs look magical at search and coding because those domains are drowning in data—and friendly to synthetic data. Most of the economy is not. Flapping Airplanes’ (Ben and Asher Spector) thesis is that data efficiency—getting coding-level capability with orders of magnitude less data—will decide who can participate in AI beyond a few centralized labs. Compute gets cheaper on a familiar curve; frontier-quality data does not. If you only optimize FLOPS, you will hit a wall shaped like contracts, compliance, and the long tail of tasks.

Define data efficiency

Data efficiency asks: can we reach valuable capabilities (the kind now seen in search and coding) with much less data—intuitively closer to how humans learn to code from far fewer examples than today’s models consume? The Spectors cite human learning gaps on the order of 10,000× to 100,000× less data than current models for coding-like skill. Whether those exact factors hold in every domain is less important than the research target: capability per token of precious experience.

This is distinct from sample efficiency as a narrow academic metric and from inference efficiency (cheaper serving). It is an economic and competitive claim about training and adaptation under data scarcity.

Why data—not only compute—is the binding constraint

Homogeneous compute vs. fragmented data. After GPT-scale models, labs could attempt to buy “all the compute.” There is no centralized data provider for the long tail. Collecting frontier-quality experience means negotiating with businesses, navigating regulation, and integrating painful operational systems. Data is getting cheaper in some senses, but not as fast or as uniformly as FLOPS.

Data-rich islands vs. the broad economy. Search roughly owns the public web; coding owns a large, synthetic-friendly slice of it. Robotics requires expensive generation and capture. Trading has finite market history. Scientific discovery often has precious little labeled signal—and unbounded upside. The memorable “toaster supply chain” line is not about appliances; it stands for tens of thousands of under-resourced workflows that compose real GDP. Those workflows will not wait for internet-scale corpora to appear spontaneously.

Competition and participation. In audience polls about AI moats, data is often the top answer. If that is true, data efficiency is what democratizes training: more companies can participate when models need less exclusive corpus. Without it, capability concentrates wherever distressed bookstores, rare libraries, and exclusive partnerships pile up—colorful examples from the talk of how hungry labs already scrape niches.

Deployment multiplier. Their economic claim is direct: a model that is on the order of 1,000× more data-efficient would be correspondingly easier to deploy into scarce-data domains. Efficiency compounds into market access, not only into nicer loss curves.

Mechanism: systems unlock algorithms

Flapping Airplanes’ technical bet is co-design: many promising learning algorithms are hard to express in today’s frameworks. PyTorch and peers intentionally synthesize a single-threaded programming model over massively parallel GPUs—write matmul, attention, norm in sequence; the runtime contorts underneath. That ease hides a smaller circle of algorithms that GPUs can actually run efficiently but frameworks make asymptotically awkward: fine-grained updates, hogwild-style parallelism, deeply pipelined loops.

Their approach lives in the gap between “what GPUs can do” and “what frameworks express.” Internally they describe a GPU virtual-machine style stack that takes over the device and implements workloads current graphs fight. History of ML, in their telling, is partly a history of new primitives for interacting with hardware—not only new chips. Mega-kernels and related low-level work are precedents; the claim is that algorithmic novelty often arrives when someone abuses existing silicon in newly expressible ways.

Builders need not copy that stack to take the lesson: your training framework is a research prior. Lock-in can hide the very algorithms that would buy data efficiency.

Failure modes

  • Treating every product line as if it had coding’s data density.
  • Synthetic data without verifiers—mountains of plausible garbage.
  • Assuming buying more GPUs substitutes for rights, contracts, and integration.
  • Framework comfort that silently forbids the algorithms you need.
  • Centralization complacency: betting the company on exclusive data without a path to efficiency if rivals catch the corpus.

Builder practices

Separate data-rich and data-poor lines of business; strategy, eval design, and model choice differ. Invest in synthetic data only where automatic or expert verifiers exist. Treat data contracts, retention, and provenance as ML infrastructure equal to cluster ops. Watch for systems bottlenecks that force inefficient algorithms. Prefer learning setups that extract more signal per scarce real episode—especially in robotics, science, and vertical ops.

Practice checklist

  • Label each major use case data-rich vs. data-poor and write different roadmaps
  • Before synthetic pipelines, define the verifier (tests, simulators, expert scores)
  • Inventory legal rights to train on production traces; fix gaps before model work
  • Prototype whether your training stack can express fine-grained / non-standard update patterns you care about
  • Measure capability per unit of proprietary data, not only leaderboard score
  • Avoid assuming search/code playbooks transfer to long-tail economy tasks
  • Track whether moat stories depend on exclusive data—and what efficiency would do to that moat

Reinforcement learning for agents is no longer only a lab technique. In Sequoia talks with Mercor’s Brendan Foody and Prime Intellect’s Will Brown and Johannes Hagemann, the bottleneck has shifted from “can we do RL?” to can we build environments that look like the economy? Without those environments, post-training reinforces eloquence in chat—not completed work.

Definition: what an RL environment is

Foody’s teaching breakdown has three parts. An RL environment is not a single prompt file; it is a packaged world an agent can act in, with a way to score outcomes.

  • Worlds — the docs, sheets, messages, slides, data rooms, and project state of real work. Example: lawyers from top firms write scenarios from real matters and outline full data rooms so the agent faces something like a live deal—not a toy paragraph.
  • Apps — high-fidelity clones of tools people actually use (Salesforce, ServiceNow, Microsoft 365, and peers), reachable via MCP, CLI, or computer-use agents (CUA). If the agent cannot operate the software stack of the job, it is not learning the job.
  • Tasks — prompts plus verifiers. Verifiers may be rubrics or unit tests; the same artifact can power eval or training. The verifier is what turns “sounds right” into “done correctly.”

Frontier labs cannot automate “everything on a laptop” without covering the distribution of worlds, apps, and tasks across jobs. Foody points at the scale of that distribution—on the order of hundreds of labor categories (e.g., GDPval-style domain coverage across Bureau of Labor Statistics job structure)—each with its own software stack. Humans remain central to constructing it, often with models in the loop.

Mechanism: why environments beat chat rubrics

Chat evals reward fluent answers. Environment evals reward state change: the ticket closed, the spreadsheet reconciled, the clause redlined against a rubric, the form submitted without schema errors.

Mercor’s published legal-environment results illustrate the mechanism with concrete post-training signal: on the order of 1,800 tasks and about $500K in compute, they report large jumps on domain metrics (e.g., corporate law moving from 4.7% to 26.6% on their reported slice), with generalization into related eval suites beyond the exact training rooms. The point for builders is not the leaderboard line—it is that modest, domain-faithful environment data can move agent competence when verifiers exist.

Prime Intellect’s “GitHub for RL environments” thesis is the ecosystem layer: share, version, and compose environments the way datasets and benchmarks standardized earlier ML eras. Their hub framing includes verifiable software-engineering environments, specialized domains (they cite examples spanning medical physics to cybersecurity), and tooling so researchers can train inside the same packaged worlds. A parallel product lesson: application companies increasingly need product–model optimization loops—Cursor-style post-training inside the real IDE environment—so institutional knowledge compounds in weights, not only in prompt lore.

Why application companies should care

RL environments used to be lab infrastructure. Now they determine whether your agent learns your workflow or a generic demo. If you only eval on chat rubrics, you will overfit to eloquence. If you train and eval in environments with verifiers, you can reinforce completed work.

That is also a moat story. Foody’s “own your intelligence” context: labs buy enormous volumes of complex tasks (he mentions frontier labs purchasing on the order of tens of thousands of tasks per month in some cases), while application companies inherit the same stack to specialize models to their domain. Expert hours—lawyers, engineers, doctors, bankers designing scenarios and rubrics—are a first-class training cost, not an annotation footnote.

Constraints and failure modes

  • Faithful app clones are expensive (and legally delicate). Thin mocks teach thin skills.
  • Verifiers are hard for fuzzy knowledge work. Easier for code, forms, and structured ops; for open-ended writing you need rubrics that experts actually agree on.
  • Expert-hour supply is its own industry. Scaling environments means scaling scarce professionals who can author worlds and tasks.
  • Benchmaxing. Once an environment is public, it risks leaking into training data and ceasing to measure what you think it measures—Prime Intellect and peers still need held-out and refreshed suites.
  • Env without train loop. A beautiful simulator that never connects to your post-training pipeline is a museum exhibit.

Practice checklist

  • Write verifiers before prompts whenever possible—score finished work, not vibes
  • Prefer environment-based evals for agent releases over chat-only rubrics
  • Invest in a thin slice of your app world (real tools + real artifacts) before buying generic agent benchmarks
  • Track expert hours as a first-class training cost beside GPU spend
  • Version environments like code: changelog, fixtures, and regression suites when apps change
  • Separate public leaderboard envs from private held-out envs to reduce benchmax leakage
  • Close the loop: the same env should support eval today and RL/post-training tomorrow
  • Start where verifiers are crisp (code, ops, structured documents), then extend to fuzzier domains with expert rubrics

Coding agents multiply how much work one engineer can push at once: more branches, more CI clones, more fetches of the same commit. Source control that was “fine” for human cadence can collapse under agent cadence—slow pushes, failed merges, reliability dips. The lesson from OpenAI’s Pando work is not “replace Git,” but rebuild the backend so Git’s protocol survives agent-scale concurrency.

Two dimensions of scale

Any distributed Git service must handle:

  1. Many writers pushing to different branches at the same time.
  2. Many readers fetching overlapping history as fast as the network allows.

Classic designs struggle when both spike together. Coordinating every ref update across full replicas (e.g. three-phase commit) serializes pushes and puts disk/network latency on the critical path. Ordering all updates through a shared write-ahead log lets pack uploads run in parallel, but competing updates to one manifest still bottleneck publication, and replicas can fall behind indexing packs before they can serve them.

Trade-offs that unlock throughput

Pando deliberately drops two assumptions many Git services treat as requirements:

  • Repository-wide point-in-time consistency. Forcing one global snapshot of every ref requires coordinating every push. Pando instead uses causal consistency: each branch is serializable on its own; a client reading several branches may see them at different moments. Humans and agents usually care about the order of updates to one ref, not a global clock across the whole monorepo.
  • Unique packfiles per client. Generating a custom pack for every fetch burns CPU and I/O. Pando reuses stored packfiles: clients may download some objects they already have, but the server can serve the same bytes from caches and saturate bandwidth.

Practically: pushes stream packfiles into blob storage, record a ref version (tip + pack + dependencies) in a scalable metadata store, and fetch becomes pack selection plus CDN/regional download—not unpack-and-repack on every server.

Negotiation that makes packs reusable

A conventional server advertises many refs so clients can omit shared objects—smaller uploads, but packs that are hard to reuse because another client may lack those omitted dependencies. Advertising no refs forces full-history packs—easy to reuse, ruinously large.

Pando’s compromise: advertise a small base (often just trunk). Feature-branch packs depend on that known base, so a reader who has trunk can usually fetch the branch with one pack. Median pack sizes stayed tiny in their monorepo; the cost is that stacked or repeated branch pushes resend more objects.

What to take away

When agents become first-class developers:

  • Measure push-to-fetch latency and concurrent branch updates—not only repo size.
  • Prefer protocol compatibility so humans and agents keep the same tools, while you change storage and consistency.
  • Treat pack reuse + per-ref concurrency as the scalability levers; treat global snapshot consistency as an optional luxury that may not survive agent load.

In production, this pattern cut median push latency nearly 5× and served nearly a petabyte of Git data per day—evidence that agent-scale engineering starts below the model: in the systems that host the work.

Imagine a “harmless” change that quietly stops millions of card and ATM transactions. For teams sitting on decades-old systems, that fear is why modernization is both urgent and hard—and why generative and agentic AI are suddenly part of a realistic path forward.

What “legacy” actually means

Legacy code still runs, but maintenance is painful. Typical traits: outdated languages, aging or unsupported infrastructure, thin or missing automated tests, little documentation, and critical domain logic that lives only in the code (and in the heads of people who may have left). It is often not a side project; it is mission-critical software nobody wants to touch because a small edit can break something downstream with no clear map of what depends on what.

These systems process money at high volume, hold patient data, or move global inventory. They are hard to maintain, expensive to scale, and increasingly fragile. Trends make the gap worse: deep COBOL and mainframe expertise is retiring while new talent trains on Python, JavaScript, and cloud-native stacks; developers burn time on debt and debugging instead of new products; unpatched platforms miss modern compliance and grow a larger vulnerability surface every year you wait.

Why the old playbook stalled

The conventional approach looked like this: assemble a team, spend months reading the codebase because docs are gone and original authors are gone, then manually rewrite or migrate piece by piece while hoping production holds. Discovery alone could dominate the calendar. Hiring more people did not automatically accelerate modernization when the scarce skill was understanding the old system.

How AI changes the phases

Generative AI can compress work that used to be purely human and mechanical:

  • Discovery — Models can read large legacy trees and produce plain-language summaries of modules, data flows, and where domain logic lives. Months of orientation can shrink toward weeks.
  • Translation — The same tools can convert languages and styles while aiming to preserve intent: COBOL to Java, C to Python, batch scripts toward event-driven or serverless forms.
  • Agentic migration — Beyond Q&A, agents can chain steps: analyze, plan, translate, write tests, and document with less hand-holding between hops.

The payoff for developers is time reclaimed from maintenance for features and innovation. Legacy systems are not vanishing; for the first time, teams have tools that can help modernize them more safely—if the workflow is designed for that.

Three modernization axes

Translating syntax is not the whole job. Successful efforts usually move on three fronts while keeping the business running:

  1. Architecture — Replace a tightly coupled monolith with smaller, independently deployable services so you can update and scale pieces without taking the whole platform down.
  2. Technology — Swap aging languages, frameworks, and on-prem stacks for platforms that get security updates, connect to cloud services, and match how developers work today.
  3. Process — Move from rare, heavily manual releases to automated testing and continuous deployment so changes stay smaller, safer, and more frequent.

Modernization is incremental: preserve decades of core logic while the substrate evolves underneath.

Limits and the human role

AI is a force multiplier, not a magic rewrite button. Models can stumble on deeply entangled domain rules. Translations may be syntactically fine and behaviorally wrong. AI can help spot or reduce some security issues, but it should not be assumed to erase existing vulnerabilities or guarantee secure code.

Results depend on workflow: testing, human review, and validation throughout migration—not only on model quality. Teams that get the most value use AI for mechanical acceleration and keep experienced engineers close to high-risk decisions. Used that way, AI makes migration faster and more thorough: better together than either pure manual rewrite or unsupervised generation.

Shift left—security from the earliest stages through the whole lifecycle—is not new, but AI-assisted development makes it non-negotiable. It is no longer enough to run a scanner slightly earlier; you need clearer answers to what you validate, when, and how you maintain confidence in machine-generated solutions.

Here are five principles for that shift.

1. Trust outcomes, not generation

AI-generated code often looks right: it compiles, runs, and may even pass shallow checks. That is not the same as being trusted. Ask whether the solution behaves securely under real conditions—permissions, data exposure, failure modes—not only whether the happy path works.

A generated service might correctly fetch customer records yet hold broader access than required, leak sensitive fields, fail open when authentication breaks, or accept malformed input that corrupts a store. Validate outcomes: least privilege, fail-safe defaults, and expected behavior when things go wrong. Generation success is a starting point, not a security verdict.

2. Security starts during generation

The old sequence—code, build, test, commit, then a late security checkbox—never worked well and collapses under AI speed. Bugs found in production are expensive; bugs found while code is still being shaped are cheap. Security defects follow the same economics.

Embed validation as code is created: static analysis, dynamic and penetration testing where appropriate, secret scanning, policy and compliance checks. The goal is fewer late surprises and fewer bottlenecks when generation takes seconds but review still takes days if left until the end.

3. Scrutinize dependencies as hard as source

AI does not only invent application logic; it pulls in packages, libraries, services, and integrations. Each dependency adds capability and risk. Teams often review generated source while overlooking what that source depends on—“out of sight” under the prompt.

Supply-chain incidents frequently originate outside your own functions. Treat generated dependencies with the same scrutiny as generated code: reputation, known vulnerabilities, licensing, source integrity, and fit to organizational standards. In AI-assisted development, dependency validation is part of secure generation, not an optional follow-up.

4. Nail intent and requirements before elegant code

Many serious issues are not syntax mistakes; they are wrong assumptions. Who may access which data? Which actions are allowed? Which business rules apply? What must stay protected? A model can produce elegant, idiomatic code that still violates policy if requirements were vague or misunderstood.

Example: a workflow correctly processes financial data yet exposes it to roles that should never see it. That is an intent failure more than a coding-style failure. Like the King Midas myth—wish granted, appetite unmet—AI will eagerly satisfy a poorly framed request. Developers become responsible for checking whether the AI solved the right problem the right way, not only whether the patch looks clean.

5. Continuous validation—and guardrails for agents

AI-assisted change is continuous, so security cannot be a one-time release gate. Confidence must be maintained: vulnerability detection (including strong modern models for discovery), dependency monitoring and patching, policy verification, and change validation after deploy. “Did it pass once?” is weaker than “does it still pass?” Security is never finished; a zero-day can sit unnoticed for decades until better tools surface it.

As work becomes agentic—multi-step actions across services, repos, pipelines, and configs—file-by-file review is not enough. Risk lives in unintended consequences across connected systems. Agents need guardrails (what they may and may not do), identities (accountability for who did what), access controls (least privilege), monitoring, and human oversight on high-impact steps. Without that, agents amplify risk instead of productivity.

The operating reality

More code, faster, means more functionality and more complexity—and complexity fights security. Speed alone does not create value; trust does. Organizations that win embed security in everyday development as continuous validation of outcomes across a growing, AI-expanded codebase—not as a compliance ritual or a last-minute gate. Shift left, keep validating, and constrain agents before they run amok.

Natural conversation has a temporal window. If synthesized speech arrives outside human turn-taking expectations, users hear awkward pauses, trust drops, and contact-center or sales agents lose the floor. Voice AI is therefore an infrastructure latency problem as much as a model-quality problem.

Why transformers struggle at the edge of perception

Many TTS stacks wait for a full text sequence before audio. Quality and latency trade off. Architectures that process audio as evolving state—state space models (SSMs) with fixed-size hidden state and token-by-token recurrence—are a better fit for streaming speech: constant memory, native streaming, long-range dependencies without quadratic attention cost. Production systems report ~90ms time-to-first-audio-byte as a realistic “feels human” target for TTS, with STT that emits partial transcripts and semantic end-of-turn detection so the LLM can start thinking before the user fully stops speaking.

Close the “wait for the whole answer” gap

Even with a fast TTS model, a common agent bug remains: the LLM generates a multi-paragraph reply, and TTS only starts after the full string arrives. Users hear silence for seconds while the answer already exists in partial form.

Fix: stream sentence by sentence (or similar phrase boundaries) from the agent to TTS as soon as each unit is complete. Host a small TTS model on a real-time GPU endpoint if you need cost control; expose both unary streaming and bidirectional WebSocket-style routes when the transport requires it. First audio can start while later sentences are still being generated.

Stop guessing autoscaling targets

TTS endpoints fail silently when scale targets are vibes:

  • Too conservative → GPUs idle on every invoice.
  • Too aggressive → concurrency exceeds what one instance can serve inside the SLO; queues explode exactly when call volume peaks.

Replace guesses with two measurements on the live endpoint:

  • Q_max — highest concurrency one instance sustains before breaching the latency SLO.
  • T_total — end-to-end scale-out time (including cold start).

Derive scale-out threshold, scale-in threshold, and cooldowns from those numbers by arithmetic. Re-measure when model, instance type, or SLO changes.

Deployment constraints

Contact centers, telehealth, and regulated workloads often need inference in-VPC with data residency. Marketplace/SageMaker-style private endpoints and careful regional placement matter as much as model choice. Pair low-latency synthesis with accurate reading of numbers, currency, and addresses when the voice stack is order-confirmation critical.

Takeaway

Budget latency like an SLO: architecture for streaming (SSM or equivalent), sentence-level handoff from LLM to TTS, and autoscaling constants measured from Q_max and T_total—not dashboard defaults.

Ricursive Intelligence’s founders Anna Goldie and Azalia Mirhoseini represent a recursive bet: use AI to design the chips that run AI. Their Google-era AlphaChip work helped design multiple generations of TPUs and cut chip floor planning from months to hours. The teaching core is not “RL cool demos”—it is closing the loop between learned placement and the painful constraints of real tapeout, then accelerating design until models and hardware can co-evolve.

Definition: AI-for-EDA vs proxy optimization

Chip design is a multi-year, often hundreds-of-millions-of-dollars bottleneck. Floor planning places macros and logic so wire length, timing, power, and manufacturability work together. AI that designs chips means learned systems proposing placements (and, broader, design decisions) inside or beside real EDA flows—not academic sketches that never meet a signoff timer.

The product lesson generalizes beyond EDA: if your reward function is not the real objective, RL will optimize the wrong world. Academic proxies such as half-perimeter wire length can look publishable and still anger chip designers who live in timing closure, power, congestion, and tool-flow reality. Successful work sits inside the real toolchain, with rewards defined by engineers who ship silicon—not only by papers.

AlphaChip-era results included unusual “alien” placements (curved and donut-like patterns) that reduced wire length, power, and timing violations—move-37 moments human designers would hesitate to try. Novelty is valuable only when the fab and signoff stack agree.

Mechanism: from fabless to designless, and co-design

Goldie and Mirhoseini describe an industry shift analogy: TSMC enabled fabless giants; Ricursive aims at designless—companies creating custom silicon without maintaining enormous in-house design teams. Asymmetric cycles today hurt co-design: AI methods evolve faster than chips can be built. Compressing design time unlocks true co-evolution of workloads, applications, and silicon—the recursive self-improvement loop where better chips train better design models that propose better chips.

Synthetic data and large-scale training on placement/design distributions matter because real tapeouts are scarce. The mechanism is not a single magic net; it is models + EDA integration + feedback from timing/power/manufacturability oracles that approximate what tapeout cares about.

Dylan Patel / SemiAnalysis themes sharpen why this matters for AI companies: hardware–software co-design is framed as a real 100× lever—not a slogan. Model sparsity and density pull toward different accelerators; teams shaped for one GPU generation struggle on another; memory bandwidth (HBM stacks today, tighter on-package memory tomorrow) dominates what algorithms can afford. CUDA’s “moat” is less a language trick than a full stack of libraries, kernels, and ecosystem. If AI shortens chip design and software is co-tuned, the cost curve of intelligence bends again—alongside energy and data-efficiency work.

Why chip design is the AI bottleneck

Neural nets existed for decades; they became practical when compute did. If chips remain the slow, expensive constraint, scaling laws stall on fabrication calendars. AI that proposes better floorplans and, eventually, broader design automation, attacks that bottleneck from inside the loop—especially for custom accelerators matched to real training and inference graphs.

Failure modes

  • Proxy reward theater. Optimizing HPWL (or any single metric) while timing/power regress in the real flow.
  • Paper-only EDA. Methods that cannot sit in production toolchains or that designers refuse to trust.
  • Ignoring manufacturability. Beautiful placements that will not yield.
  • Co-design theater. Buying GPUs while treating model architecture as hardware-agnostic forever—then wondering why a sparse expert model hates your accelerator.
  • Cycle mismatch. Assuming software can wait years for the “perfect” chip without intermediate co-optimization.
  • Talent myth. Believing designless means zero chip expertise; you still need people who can define rewards, constraints, and signoff.

Practices for AI builders (even if you never tape out)

Treat reward design as product management: write the real objective (latency at batch size B, $/token, joules/token, yield) and refuse proxies that diverge. Prefer co-design checklists when choosing model shapes (sparsity, precision, memory traffic). Track goodput and bandwidth, not only peak FLOPs. If you use learned autosystems (compilers, schedulers, placement), demand ablation against the metrics ops will fire you for.

Practice checklist

  • Name the true objective (timing, power, $/token, joules) before choosing a learning reward; document proxy gaps.
  • Integrate learned tools into the real EDA or compiler flow early—refuse offline-only demos as launch criteria.
  • Include designer-in-the-loop review for trust and constraint capture; measure override rates.
  • Use synthetic + historical design data deliberately; watch distribution shift vs your next node/process.
  • For model↔chip co-design: match sparsity/density and memory traffic to the target accelerator family.
  • Budget for iteration speed (hours/days vs months) as a first-class roadmap goal—slow loops kill co-evolution.
  • Prefer full-stack evaluation (libraries, kernels, interconnect) over single-kernel peaks when claiming speedups.
  • If pursuing “designless” custom silicon, still staff constraint owners who can say no to unsafe proposals.

  • Organizations that instrument failures for process change—not only model fine-tunes.
  • Layered stacks: learned components plus maps/simulation/policy where needed; avoid “end-to-end or bust” absolutism in deployment rhetoric.

Language models pretrain on the internet. Robotics has no equivalent corpus. Sequoia’s conversations with Mecka’s Josh Gao, NVIDIA’s Jim Fan, Physical Intelligence’s Karol Hausman and Tobi Springenberg, and Hugging Face’s Thomas Wolf converge on a manufacturing problem: how to produce physical experience at scale—and then distribute skills the way software platforms distribute apps.

Definition: what a robot data factory is

A robot data factory is an industrial system for creating, cleaning, and licensing the multimodal trajectories that train physical AI: pixels (what the world looks like from an embodied POV), actions (how bodies move and grasp), and logic (task structure and success criteria). Gao’s Mecka thesis is blunt: robotics is data-constrained in a way LLMs were not. The cold start is not free web text; it is paid collection, sensorized humans, partner sites, and quality gates.

Egocentric data—first-person video of humans demonstrating tasks—is a core feedstock. Robots experience the world from a POV; showing them human POV closes much of the vision gap even before you solve full embodiment transfer. Earlier egocentric corpora (Gao cites Ego4D-scale collections on the order of thousands of hours) proved the format but often captured daily life rather than task-complete industrial trajectories. A factory’s job is to make the distribution match what policies need: diverse, labeled, success-complete work—not bowling highlight reels.

Mechanism: from human sensing to generalist robots

Think of the stack in layers.

1. Capture hardware and ops. Wearables and sensorized humans turn people into temporary robots—recording rich demonstration without waiting for a perfect humanoid fleet. Ops matter as much as sensors: which tasks, which environments, which worker partners, and which quality gates decide whether a take enters training.

2. Multimodal warehousing. Trajectories must stay aligned across video, proprioception/actions, and task metadata. “Lots of video” without action labels and success flags is a content library, not a training factory.

3. Foundation models for the physical world. Fan’s NVIDIA GEAR framing describes a three-pronged data strategy—internet-scale priors, simulation, and real robot data—aiming at a foundation agent that generalizes across skills, embodiments, and even physical vs. virtual realities. Historical LLM pattern he emphasizes: specialists first, then generalists, then specialized generalists (prompt/fine-tune/distill the generalist back onto a task)—and the specialized generalist usually wins. Robotics is still climbing toward that generalist moment across embodiments.

Physical Intelligence states the endgame explicitly: robotic foundation models that, in principle, let any robot do any task. Their claim is that robotics has been held back less by hardware than by an intelligence bottleneck foundation models can attack—end-to-end learning of generalizable behavior rather than task-specific programs, with real-world deployment and RL-from-experience to push past pure imitation.

4. Distribution layer. Wolf’s Hugging Face angle is platform economics: once basic building blocks exist, an “app store” dynamic for robot skills and physical AI components can emerge—open distribution of models, datasets, and tools so builders compose rather than recreate the stack. Data remains the bottleneck; openness is a bet that shared infrastructure accelerates everyone the way Hub ecosystems accelerated NLP.

Constraints unique to physical AI

  • No free pretraining dump. Every useful hour is expensive; commercial unlocks (simple pick-and-place first, then the long tail) pace the economically feasible scale.
  • Embodiment and sim-to-real gaps. Simulation helps (Fan highlights NVIDIA’s graphics advantage and even LLMs writing reward functions for self-play), but transfer still bites.
  • Safety has physical consequences. Failed policies bruise people and property, not just reputation scores.
  • Social and rights friction. Workplace instrumentation, worker consent, and data licensing are load-bearing product decisions—not afterthoughts.
  • Long-tail task diversity. The easy demos are not the economy; Gao notes the long tail is orders of magnitude larger than early unlocks.

Failure modes

  • Robot SKUs before data ops. Buying arms without a capture → warehouse → train → redeploy loop.
  • Internet-video cosplay. Scraping third-person web video and calling it robotics pretraining without action/logic alignment.
  • Demo theater. One-off teleop videos that do not survive distribution shift across sites, lighting, objects, or operators.
  • Specialist dead ends. Shipping a narrow picker that cannot absorb a foundation-model upgrade path (Fan’s warning: specialists are easier short-term; generalists unlock the compounding loop).
  • Ignoring the platform layer. Training a closed skill with no path to share, version, or compose—then rediscovering Hugging Face-style distribution pain later.
  • Underfunding quality gates. Volume without curation teaches robots the wrong world.

Practice checklist

  • Design data capture (sensors, consent, task taxonomy) before scaling robot SKUs
  • Prefer tasks with crisp success criteria so imitation and RL get a real learning signal
  • Budget continuous data ops—collection, labeling, relicensing—not a one-off demo sprint
  • Mix internet priors, sim, and real trajectories deliberately; measure sim-to-real failure explicitly
  • Separate fleet reliability engineering from model research early (broken robots poison data and trust)
  • Plan for specialized-generalist fine-tunes once a generalist base exists—don’t only accumulate one-off specialists
  • Treat open distribution (datasets, policies, evals) as a growth loop if you want an “app store” ecosystem
  • Instrument data rights and workplace policy as part of the ML pipeline, not as legal cleanup

ElevenLabs’ Mati Staniszewski argues that voice is becoming a fundamental interface layer—not a niche accessibility feature bolted onto chat. As generative speech crosses the uncanny valley across languages, products can meet users where emotion, speed, and hands-free work already live: calls, games, cars, clinics, warehouses, and creative media. The strategic bet is infrastructure for voice agents and real-time translation, not another one-off demo voice.

Definition: voice as interface, not feature

An interface is the primary way humans and systems exchange intent. Keyboards and touchscreens dominate knowledge work; voice has always dominated human-to-human work. “Voice as interface” means the product’s main loop is listen → reason/tool → speak (and interrupt), with text as a secondary channel—not TTS sprinkled on a form.

ElevenLabs stayed laser-focused on audio while foundation-model labs chased broad multimodal. That specialization—transformers and diffusion applied to speech, with scarce audio talent hired globally remote—produced usable narration, dubbing, agents, and consumer virality (from creators to Fortnite’s Darth Vader). Focus is part of the definition: voice quality, latency, and reliability are hard enough that treating speech as a side quest usually loses.

Why voice works now

Three product thresholds matter. Quality must clear different bars for audiobook narration, dubbing, and agent delivery. Latency must be low enough for conversation; without it, you do not have an agent—you have a voicemail. Reliability must hold at scale (millions of concurrent players in a game title, not a conference-room demo).

Prosumer-first distribution accelerated learning: releasing models to creators surfaced unexpected use cases (viral videos, “no face” channels, authors pasting whole manuscripts) and created bottom-up demand that later pulled enterprise. Media peers normalizing AI-native audio and video (music, generative video) further reduce user stigma. Real-time translation—keeping speaker identity while changing language—points at a world where language barriers shrink inside the same voice channel.

Mechanism: full stack around the model

Breakthrough weights are not a product. Staniszewski’s stack story is the teaching mechanism: voice coaching and emotional labeling, proprietary data pipelines (how something should be said, not only what was said), speech-to-text paired with TTS, developer tooling, and integrations into telephony (e.g. Twilio) and CRMs so agents live inside existing workflows. Researchers sit close to deployment for tight feedback loops.

Conversational agents need interruption and turn-taking: users barge in, correct, or abandon. Quality-versus-latency tradeoffs are explicit product knobs. Voice without tools is theater; voice plus an agent harness (retrieval, CRM actions, payments, ticketing) is a product. Creative workflows (dubbing, localization) and agent workflows share infrastructure but not the same SLOs—do not ship one latency budget for both.

In the rocketship conversation with Lovable’s Anton Osika, the shared pattern is rapid product iteration under foundation-model churn: stay nimble when a new model drops, integrate within hours, and keep depth in the domain (voice or software generation) rather than becoming a thin wrapper. Scale is research and deployment ops.

Failure modes

  • Latency theater. Beautiful samples in a studio; multi-second gaps on a live call. Conversational UX dies first.
  • Voice without agency. Reading FAQ scripts aloud does not justify the interface; users expect actions.
  • Consent and clone risk. Cloned voices are brand and regulatory hazards. Safety mechanisms that help good actors and limit misuse are part of the product, not a policy PDF after launch.
  • One-size quality. Narration thresholds ≠ agent thresholds ≠ dubbing thresholds. Mixing them burns trust.
  • Model-only competition. Hyperscalers can ship speech models; switching costs come from data pipelines, coaching, integrations, and reliability at scale.
  • Ignoring interruption. Systems that cannot handle barge-in feel broken even when WER/MOS scores look fine.

Builder practices

Treat voice as a systems problem: capture, VAD, streaming ASR, LLM/tools, streaming TTS, telephony, observability. Instrument time-to-first-audio and time-to-interrupt as primary KPIs. Ship consent flows and watermarking/abuse tooling where cloning is offered. Use prosumer or internal dogfood to find weird use cases before enterprise RFPs freeze the wrong roadmap. Pair every voice surface with a tool policy: what the agent may say and do.

Practice checklist

  • Pick one primary mode (agent call, narration, dubbing) and set explicit quality/latency/reliability targets for it.
  • Measure time-to-first-byte/audio and barge-in success; gate launches on those, not only MOS.
  • Wire tools (CRM, calendar, payments) before polishing persona; refuse “talking brochure” scope.
  • Ship consent, auth, and misuse controls with any clone or custom-voice feature.
  • Build data loops for emotion/prosody labeling—not only transcripts.
  • Integrate into the channels users already inhabit (phone, game, browser), not only a web widget.
  • Separate creative vs conversational SLOs and model variants.
  • Plan for foundation-model shocks: swap path within days without rewriting the harness.

AI that designs proteins and genomes accelerates medicine—and complicates biosecurity. Novel sequences may not match known-threat databases, so DNA synthesis screening cannot assume “unfamiliar ≈ natural.” DeepMind’s SynthID Bio and broader bioresilience framing teach layered defense with provenance in the design itself.

The new failure mode

Classic screening compares orders to catalogs of dangerous sequences. Generative models can invent functional sequences with little resemblance to known hazards, forcing slow manual review—or missed risk. Public structure/sequence databases also face pollution from mislabeled synthetic entries that skew downstream science and security decisions.

SynthID Bio: watermark the molecule, not only the file

SynthID Bio adapts watermarking to biology:

  • subtly guide amino-acid choices in sequences;
  • adjust atomic coordinates in predicted structures;
  • aim for a signal detectable on the physical synthesized protein, not just a digital file.

Wet-lab tests on watermarked protein binders (with AlphaProteo / ProteinMPNN-style pipelines) reported matched hit rates, binding affinity, and diversity versus non-watermarked designs across several targets. For folding, fine-tuning part of AlphaFold 3’s diffusion pathway embeds detectability while preserving accuracy.

Early work with genomic models (e.g. Evo 2 bacteriophage designs) explores watermarking more complex biological objects while keeping function in culture.

Swiss-cheese defense

No single control is enough. Layers include model mitigations, customer vetting, synthesis screening—and watermarks as a verification layer linking an order to a trusted model developer. Synthesis providers can then streamline screening for watermarked, safeguarded-model outputs and focus human review elsewhere. Pairing with metadata standards (C2PA-like for biodesign) or central registries strengthens provenance further.

Open methods, code, in vitro data, and weights for research are part of the adoption strategy: biosecurity tooling needs community scrutiny to keep pace with generative capability.

AlphaGenome Atlas: precompute the variant map

Separately, AlphaGenome Atlas precomputes predicted molecular effects for on the order of 9 billion possible single-letter human genome variants—turning a model that analyzes specific variants into an atlas researchers can query. The teachable parallel: when exhaustive wet-lab testing is impossible, precomputed AI maps become scientific infrastructure (with appropriate research access controls).

Lessons

  1. Treat generative bio as dual-use infrastructure; design verification into the artifact.
  2. Preserve biological function as a hard success criterion for any watermark.
  3. Stack defenses; watermarks complement—not replace—screening and access policies.
  4. Publish measurement methods so synthesis providers and databases can actually use the signal.
  5. Precomputation (atlases) and provenance (watermarks) are both ways AI becomes shared scientific utility.

Scientific AI is moving from “answer a biology question” to agents that run discovery workflows—curating literature and structures, calling domain tools, proposing designs, and debating hypotheses. Two DeepMind lines illustrate complementary patterns: Antigravity Cheminformatics Skills and Co-Scientist.

Pattern A: LLM orchestrates; deterministic tools calculate

Cheminformatics in Google Antigravity targets a classic bottleneck: molecules appear as IUPAC names, patent Markush drawings, SDF files, chart images—and a single atom error describes a different compound. The skills:

  • let the language model handle orchestration, database navigation, and scientific reasoning;
  • delegate molecular calculation to RDKit and curated sources (ChEMBL, PubChem);
  • encode medicinal-chemistry best practices into the agent workflow.

A walkthrough rigidifying lung-cancer TKIs (crizotinib → lorlatinib-style macrocycles) shows an hour-scale loop: literature harvest → filtering → interactive visualization → matched molecular pair analysis → potency models with scaffold/chronological splits → novel designs with synthesis rationales and electron-pushing diagrams.

Hard constraint taught explicitly: sparse assays and lab noise limit predictive precision; computational designs are hypotheses to synthesize, not finished drugs.

Pattern B: Multi-agent scientific debate

Co-Scientist (Gemini-based, reported in Nature) mirrors how scientists actually think: generate → critique → refine. Specialized agents:

  • Generate — propose hypotheses; proximity clustering for diversity.
  • Debate — reflection as virtual peer review; ranking via pairwise “idea tournament” (AlphaGo/AlphaStar-inspired Elo-style competition).
  • Evolve — combine top ideas; meta-review synthesizes a research proposal.

A supervisor plans in freeform, parallelizing exploration. Most compute goes to verification against literature and databases (web search, ChEMBL, UniProt; specialized models like AlphaFold in collaborations)—so novelty stays grounded.

Field examples (liver fibrosis drug repurposing, ALS collaboration sparks, aging genetic leads) emphasize Co-Scientist as a collaborator that has read widely, not an autonomous lab.

Shared lessons for science AI

  1. Division of labor — fuzzy reasoning vs exact chemistry/physics tools.
  2. Interactive artifacts — viewers, plots, proposals a human can challenge mid-loop.
  3. Verification-heavy compute — debate and grounding beat one-shot brainstorming.
  4. Human-in-the-loop wet lab — agents compress iteration time; experiment remains the judge.
  5. Domain skills packages — reusable workflows (cheminformatics, hypothesis generation) beat generic chat with PDFs.

Weather and land-cover AI convert research models into decision infrastructure—hourly forecasts in consumer products, energy and agriculture variables, and forest maps that distinguish what “green” actually is.

WeatherNext 3: from physics grids to observation-driven forecasts

Traditional numerical weather prediction leans on physics simulations. WeatherNext 3 emphasizes learning from real-time observations, including hourly geostationary satellite mosaics, to refresh forecasts more often and at sharper resolution.

Teachable upgrades:

  • Resolution — surface variables down to ~5 km (vs ~25 km / 6-hour steps in the prior generation), with coarser grids for some atmospheric fields—about 5× sharper overall.
  • Architecture sketch — a Functional Generative Network (FGN) mesh transformer ingesting live satellite data plus historical analysis; outputs dense grids, cyclone tracks, and station-level points.
  • Productization — integration across Search, Maps, Gemini, Maps Platform, and Cloud so accuracy gains reach users and developers.
  • Domain variables — precipitation quality and clean-energy-relevant fields, tying forecasts to agriculture and renewables—not only umbrella decisions.

Independent live evaluations (e.g. Brightband) are used as external validation—another instance of “don’t only trust in-house scores.”

Beyond tree cover: forest typology

From space, old-growth rainforest, eucalyptus plantation, and oil palm can look like the same green. Carbon and biodiversity differ radically. ForTy 2020 (with WRI and IIASA) maps every 10×10 m patch into forest/land-use types and tracks yearly change (2017–2025 early series)—not just loss of tree cover, but what replaced it. That typology is a baseline for regulations such as the EU deforestation rules.

Why this is teachable AI practice

  1. Task definition beats model hype — “tree cover” was the wrong label for conservation; typology fixed the question.
  2. Operational cadence — hourly refresh and product embedding matter as much as benchmark RMSE.
  3. Multi-resolution outputs — match spatial/temporal detail to the decision (local topography vs global wind).
  4. Partnerships — scientific institutes and agencies turn models into shared maps and forecasts others can rely on.

Related cyclone-focused WeatherNext work and AlphaEarth-style planetary mapping extend the same theme: Earth systems as first-class AI application domains with public-good distribution.

Modern experiments produce more data than any lab can thoroughly read. The complementary problem for AI-produced proofs and papers: raw model output is not yet scientific understanding. Two practices address the two sides—parallel agent exploration of large datasets, and community stewardship of AI discoveries.

Thousands of agents on biological atlases

A workable pattern for complex omics-style data:

  1. Partition analysis across thousands of agents (domain-tuned models) so each examines a slice of gene-perturbation / cell-atlas results.
  2. Force agents to connect experimental effects to scattered literature—not only restate tables.
  3. Compress wall-clock time from months of human browsing to tens of minutes of coordinated compute.
  4. Treat outputs as leads and questions for wet-lab and domain experts, not as automatic medical claims.

The educational point: AI’s comparative advantage is exhaustive combinatorial exploration of “what might matter” in datasets built for discoveries the creators did not foresee. Human scientists remain the judges of which leads become programs.

Release AI research results as raw material

When frontier models produce novel math/CS/physics results, dumping a PDF as if it were a human paper can confuse credit, exposition, and verification. An experimental release menu:

  • Math: publish AI output; let the community self-organize explanations.
  • CS: form an external collaborator group to explain while making AI output public.
  • Physics: form collaborators and defer to them on what materials to release.

Shared principles: transparency (no NDAs silencing discussion), no lab claim of academic credit for the discovery, recognition for shepherds who turn raw results into understanding, and funding/compute for communities (e.g. mathematics initiatives) to digest AI output.

Why both matter together

Agent swarms without scientific process create noise. Traditional publication norms without agent-scale exploration leave data unread. The teachable synthesis: use agents to expand the search frontier; use human communities and shepherds to convert findings into reliable knowledge.

Harvey’s Gabe Pereyra frames the problem without romance: competing with frontier labs from the application layer is an unfair game—they have more money, talent, compute, and data. The alternative title of his talk is blunt—building a research lab on a budget. The broader Sequoia pattern is that application companies are becoming research orgs because domain intelligence is the moat, and generic frontier models will not specialize themselves into professional workflows. Jerry Tworek and Rohan Anil’s Core Automation discussion adds a caution from the AGI-lab side: scaling RL in the lab does not automatically transfer to messy deployment. Chai Discovery’s “bitter lesson” for drug design rhymes from science: treat the workflow as a scaling problem with the right learning setup, not only as artisan craft.

What an applied research lab is (and is not)

An applied research lab inside a product company is a team that produces model behavior and evaluation assets for a vertical—not a miniature OpenAI pretraining cluster. Its outputs are typically:

  • Domain benchmarks that public leaderboards miss (legal diligence unit tests, binder assays, security win-rates)
  • Post-training recipes and tool-use policies for professional workflows
  • Data engines from production traces and expert-guided synthetic data
  • Tight pairing of researchers with product, GTM, and customer reality

It is not recreating full pretraining. Pereyra’s playbook starts from the frontier ecosystem: use foundation models as a substrate, then out-specialize labs on the vertical they cannot see.

Mechanism: how a budget lab competes

1. Benchmarks before training. Without a good benchmark you cannot train; without training you cannot claim frontier intelligence in-domain. Harvey’s diligence example: large suites of unit-test-like checks that turn fuzzy legal work into scoreable tasks. Evals are product infrastructure, not a research side quest.

2. Domain experts as data directors. Privileged customer data often cannot enter generic models—or even the vendor’s own weights. What started working for Harvey: lawyers guiding coding models to generate realistic synthetic datasets for training and evaluation—analogous to engineers “vibe coding” rather than hand-writing every line. Synthetic data is a bootstrap, then scaled with partners; it is not a substitute for real traces forever.

3. Efficient RL environments. As datasets grow, evaluation cost explodes. The applied lab’s systems work is turning tasks into environments the model can practice cheaply—exactly the same shape as frontier RL, but scoped to vertical verifiers.

4. Post-training with neo-labs, serve in production. Partner for weight updates you cannot afford alone; own serving, tool wiring, permissions, and product UX. The moat is the loop: production → data → eval → post-train → production.

5. Scientific scaling where verifiers exist. Chai’s bitter-lesson bet: scale data, models, and compute so the model learns what hand-built chemistry pipelines miss. Reported results in their talk—moving de novo antibody design hit rates from a sub-0.1% regime toward much higher rates—illustrate why applied science labs obsess over measurable design loops, not slideware “AI drug discovery.”

Why labs that own real environments win

Tworek’s disappointment with “train in the lab, deploy in the world” is a structural lesson for application companies. Transformers carried workflow automation extraordinarily far; the next failures appear when the world shifts—new tools, codebases, relationships, events—and offline corpora go stale. An applied lab sitting on live customer environments, permissions, and outcome metrics has a transfer advantage frontier generalists lack. The risk flips: without research discipline, that same production access becomes anecdotal fine-tuning and eval theater.

Failure modes

  • Fake lab, real burn. Hiring a few PhD titles without benchmarks, data contracts, or production hooks.
  • Competing on pay packages alone. Pereyra calls early researcher-poaching against Anthropic-scale offers a mistake; domain experts who will touch customers and pipelines often unlock more than a single frontier researcher who never sees a workflow.
  • Leaderboard cosplay. Optimizing public exams that lawyers/doctors/chemists do not actually perform.
  • Synthetic-only complacency. Synthetic sets start the flywheel; without production feedback they drift.
  • Lab–deploy split. Beautiful RL in simulation that never meets identity, audit, and latency constraints.
  • Artisan refusal to scale. In science especially, hand-crafted features that do not benefit from more data/compute lose to bitter-lesson setups when you have the right learning problem.

Practices that work

Fund evals like reliability engineering. Hire hybrid profiles: researchers willing to sit with customers, and domain experts willing to steer models. Prefer problems with verifiers (tests, binders, win-rates, cycle time). Publish enough method to recruit; keep the data engine and proprietary evals closed. Use frontier APIs and neo-lab partners for undifferentiated training muscle; spend internal research on what only you can score.

Practice checklist

  • Ship a vertical benchmark before a custom training run
  • Instrument production for traces you are legally allowed to learn from
  • Pair every researcher with a domain owner and a clear verifier
  • Budget eval compute explicitly—it grows with dataset ambition
  • Decide what you post-train vs. what you prompt/tool around a frontier base
  • Recruit for contact with reality, not only paper prestige
  • Publish selectively; treat the data engine as proprietary infrastructure
  • Re-run transfer tests in real permissions/latency environments, not only offline scores

Demis Hassabis’s Sequoia conversation is notable for calibrated optimism: AGI as a multi-decade mission that, in his telling, has stayed roughly on the schedule DeepMind sketched around 2010—and for which he still names roughly 2030 as a distribution year. The useful teaching point is not a scoreboard percentage. It is that remaining gaps are conceptual and architectural, not only “buy more GPUs.” Across Hassabis, David Silver’s “superlearner” bet, and Pushmeet Kohli’s AI-for-science stack, a shared picture emerges of what “mostly there” means—and what still breaks when builders treat today’s chatbots as finished AGI.

Define the destination before counting progress

AGI, in these talks, is not “a very good assistant.” Hassabis’s original DeepMind framing was blunt: solve intelligence, then use it to solve everything else. That implies a system that can generate and test knowledge in the world—science, medicine, simulation—not only regurgitate text. Silver sharpens the same idea as a superlearner: an agent with depth (start from knowing nothing and discover far beyond human priors) and breadth (drop into any stream of experience—simulated, digital, or physical—and keep learning).

That definition matters for product strategy. If AGI means open-ended discovery from experience, then LLM fine-tunes on human data are a powerful phase, not the end state. Silver’s critique of today’s labs is precise: much “scientific discovery” still has heavy human-in-the-loop scaffolding; embodied and non-linguistic domains (plasma control, radio towers, robot arms) may not even fit a language-first paradigm. Counting progress against the wrong destination produces false confidence.

Mechanisms that got us “this far”

Several phase changes explain why the field feels close:

  • Deep learning + reinforcement learning at scale. Hassabis describes DeepMind’s early bet as combining two then-siloed academic traditions, plus accelerated compute—ideas that looked sci-fi when expert systems still dominated MIT and Cambridge. Games (Go, chess) were the proving ground because they offered perfect simulators and clear reward.
  • Removing human priors where they limit discovery. Silver’s AlphaZero lineage is the teaching example: once human game data is set aside, the agent can shoot past human style and keep climbing an open-ended learning curve. The same logic argues against forever breadcrumb-trailing RL toward hand-specified “science” objectives.
  • Foundation models + harnesses for science. Kohli’s FunSearch / AlphaEvolve pattern pairs generative models with evaluators—programmatic judges that distinguish hallucination from insight. AlphaFold showed classical neural nets can approximate problems once thought to require quantum modeling; AlphaEvolve shows LLMs plus evolutionary search can improve decades-old algorithms when a trusted scoring function exists.
  • World models and simulators. Hassabis emphasizes learned simulators (weather, virtual cells) as the bridge from AI-as-tool to new sciences of emergent systems—economics, biology—where controlled experiments are otherwise impossible.

None of these mechanisms alone is AGI. Together they explain why coding and math feel transformed while robotics and open-world science still feel hard.

What still blocks the last mile

Continual learning / age of experience. Static pretraining on a frozen corpus is not the same as a system that discovers forever. Silver’s “crucibles”—environments rich enough for intelligence to emerge from simple objectives—are still research, not commodity product infrastructure. Without experience loops, models remain brittle when the world changes: new tools, new codebases, new events.

Verifiers and data scarcity outside search/code. Kohli is explicit: AlphaEvolve-class systems work wherever you can find a trustworthy function evaluator. Domains without cheap, objective evals (messy enterprise judgment, much of wet-lab biology until digital–physical validation closes) do not automatically inherit coding-level progress.

Agency vs. tool. Hassabis recommends building an extremely capable tool first, then carefully crossing into questions of autonomous agency and consciousness. Builders who skip that order—shipping unbounded agents into production without audit, scope, or evals—confuse demo autonomy with reliable agency.

Transfer from lab RL to messy deployment. Related talks (e.g. Core Automation’s founders) stress a structural tension: models trained in the lab, deployed in the real world. Scaling RL inside a clean environment does not automatically transfer. That gap is part of the “last mile,” even if base models keep improving.

Failure modes for builders

  • Capability freezing. Roadmaps that assume today’s model ceiling for three years will under-build abstraction layers that absorb new generations.
  • Domain wishful thinking. Treating every vertical as “one fine-tune from coding performance” ignores missing verifiers and experience data.
  • Human-prior lock-in. Over-weighting imitation of expert traces can cap discovery; sometimes you need environments and rewards that allow surprise.
  • Evaluator theater. Fancy agents without trusted scoring functions produce confident nonsense at scale.
  • Science theater. Claiming “AI scientist” without closed-loop experiment design (digital proposal → evaluator → optional wet-lab validation) is branding, not mechanism.

Builder practices

Prefer architectures that swap models without rewriting workflows. Invest in domains where you can create experience loops and verifiers—unit tests, binders, simulations, human expert raters at known cost. Treat science and robotics products as verifier-and-data problems first. Plan for continual learning: capture production traces, allow controlled on-policy improvement, and expect re-training when tools change. Use frontier models as tools inside harnesses; do not wait for a mythical single AGI checkpoint before shipping narrow, measurable autonomy.

Practice checklist

  • Write down your AGI-relevant definition (tool vs. superlearner vs. chat quality) so roadmap debates stay honest
  • List which product surfaces have trusted evaluators today—and which are aspirational
  • Design for model churn: routing, eval harnesses, and prompt/tool contracts that survive new releases
  • Prefer problems where agents can act, observe, and be scored without a human on every step
  • Separate demo agency (long tool traces) from production agency (scoped permissions, logs, rollback)
  • Budget for environment/crucible engineering, not only inference spend
  • When claiming scientific AI, specify the digital→physical validation loop
